開発項目 `$ARGUMENTS` に着手する。`doc/workflow.md` の **G1（計画合意）** を通すための手順。

> [!IMPORTANT]
> **このコマンドは計画書を作って G1 を通すところまで**。実装には進まない。
> §4「ユーザー確認事項」の合意が取れてから着手する。

---

## 1. 着手前の確認

### 1-1. 既存の課題リストを見る

```powershell
Select-String -Path doc\issue_list.md, doc\issues\*.md -Encoding UTF8 -Pattern "<関連しそうな語>"
```

関連する課題があれば、**優先順位をユーザーに提案する**（`doc/project_knowhow.md` D-1）。
既に起票済みの項目に着手する場合は、issue の記述を計画書へ引き継ぐ（二重管理を作らない）。

### 1-2. 仕様書を読む

非自明なバックエンド変更なら、着手前に該当箇所を読む。**計画書はこれを読んだ上で書く**。

- `doc/architecture.md` — 全体構造、T1〜T5 パイプライン
- `doc/backend_specification.md` — DB スキーマ、カラム意味、指標の式、API 契約
- `doc/frontend_specification.md` — 画面仕様
- ドメインが明らかなら対応する `.claude/skills/<name>/SKILL.md`
  （スキーマ・indicator・パイプラインに触れるなら **sandbox-workflow は必読**）

### 1-3. 変更種別を見立てる（§10.2）

ここで **B / C だと分かったら、作業環境の準備方法が変わる**。

| 種別 | 作業環境 |
| :--- | :--- |
| A（コードのみ）・D（設定・文書） | 本体チェックアウトで可。ワークツリーを切るなら `--mode read` |
| **B（データ形状）・C（ユーザー資産 DB）** | **ワークツリー＋`--mode write`**（`doc/agent_execution_rules.md` §10.3） |

バックテスト・最適化も `--mode write` が要る（`optimization_runner` が `init_db()` を呼ぶため）。
`pytest backend/tests/` 全体を回す場合も同じ。

## 2. 計画書を作る

```powershell
Copy-Item doc\in_progress\_TEMPLATE.md doc\in_progress\$ARGUMENTS`_plan.md
```

テンプレートの `<>` とコメントは記入時に削除する。特に次の欄は**手を抜かない**。

### §1 背景と目的 — ベースラインを数値で残す

性能・品質系のタスクは、**着手前の実測値を必ず記録する**。
完了後に「良くなった」と言うための唯一の根拠になる。後から測り直すことはできない。

### §2.2 変更しないこと（確定した設計判断）

検討して「やらない」と決めた案とその理由を `| 論点 | 判断 |` の表で残す。
レビューの蒸し返しを防ぐだけでなく、**引き継ぎ先のエージェントが同じ案を再提案するのを防ぐ**。

### §4 ユーザー確認事項 — 合意形成の核

- 破壊的変更・非互換
- 手動操作が必要な項目
- 未解決の設計判断
- **数値を決め打ちする箇所**（閾値・タイムアウト等）は、根拠の有無を明記する

確認事項が無い場合も「なし」と明記する。

### §5 チェックリスト — 再開点になる

着手順に並べる。TDD なら**テスト作成を実装より前に置く**。
ドキュメント更新・後片付けまでタスク化する。
**影響の小さい項目から並べる**と、途中で中断しても被害が小さい。

### §6.1 反証 / §6.2 転記の完全性 — 計画時に書く欄

- **§6.1**: 「この結論が誤りだとしたら何が観測されるはずか」を**着手前に**書く。
  完了後に書くと、出た結果に合わせた後知恵になる。
  **可能なら独立経路での確認も着手前に実施する**（運用データが要る場合のみ後回しにし、
  そのときは**測る契機をどこに置くか**まで決める。「後で測る」は実施されない）。
- **§6.2**: 会話・issue・別の計画書から項目を転記した場合は**件数を突き合わせる**。
  転記が無ければ「なし」と書く。

## 3. ユーザーレビュー（G1）

計画書を提示し、**§4 を中心に合意を取る**。ユーザーが判断する地点は G1 / G4 / G5 と
エスカレーション条件だけなので（`doc/workflow.md` §2）、**実装中に聞きたくなりそうな論点はここで出し切る**。
以下を明示的に伝える。

1. スコープ（何をやり、何をやらないか）
2. §4 の確認事項と、こちらの推奨案
3. 変更種別と、それに伴う作業環境（B / C ならプロビジョニングが要ること）
4. 想定する作業量とチェックリストの区切り

**合意が取れるまで実装に進まない。** 合意後は `/accept` で G2（項目検収）を通しながら進め、
実装系の項目が揃ったら `/accept` がそのまま G3（ブランチレビュー）を自動で実行する。

---

## 4. 作業中の運用

- チェックリスト・作業中メモ・§7 途中発生した課題を**随時更新する**。
  別セッションからの再開点になるため、区切りごとに即時更新すること
- ワークツリーで計画書を更新したら**その場でコミットする**（未コミットで置き残さない）
- 完了したら §6 の結果を記入し、`doc/completed/` へ移動する。対応した issue は
  `doc/issue_list.md` から `doc/issue_list_archive.md` へ移す（`doc/issues/` の詳細も含めて）
