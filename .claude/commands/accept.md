成果物を検収する。ゲート・判断者・上限・閾値の定義は **`doc/workflow.md`**。
本コマンドはその G2（項目検収）と G3（ブランチレビュー）を実行する手順である。
数値はここに書き写さず、`doc/workflow.md` §3 を参照すること。

検収は2段ある。**G2 は「動くか＋計画どおりか」、G3 は「意図を満たしているか」**で、目的が違う。
G2 だけでは、実装もテストも通るが意図を満たしていない欠陥が素通りする
（実例: WAL チェックポイントが「呼んでいるのに一度も効いていない」状態に誰も気づけなかった件）。

**このコマンドの実行中はユーザーに確認を求めない。** 止めてよいのは
`doc/workflow.md` §2.1 のエスカレーション条件に該当したときだけ。

---

## G2: 項目検収（チェックリスト項目ごと・全変更で必須）

### G2-1. 差分を読む

```powershell
git diff                      # 本体チェックアウトの場合
git diff main..<branch>       # ワークツリーの場合
```

**計画書に書かれていない変更が混ざっていないか**を最初に見る。混ざっていたら、
それが必要な変更なのか、ワーカーの逸脱なのかを判断する（逸脱なら計画書を更新してから受け入れる）。

### G2-2. テスト全体を実行する

```powershell
.\venv\Scripts\python.exe -m pytest backend/tests/ -q
```

対象ファイルに絞った実行はワーカー側で済んでいる。**ここでは全体を回す**
（他を壊していないことの確認が検収の目的）。フロントエンドに触れた場合は `cd frontend; npm test` も。
ワークツリーで既知の1件だけが落ちる場合は `doc/agent_execution_rules.md` §10.3 を参照（環境要因）。

### G2-3. 変更種別を判定する

`doc/agent_execution_rules.md` §10.2 の A〜D。**完了報告に必須記載**（merge 後の処理と G3 の対象が変わる）。

### G2-4. 受け入れ条件との照合

差分を**計画書の受け入れ条件と突き合わせる**。
「テストが通った」ではなく「**計画書が要求したことを、コードが実際に満たしているか**」を見る。

- 計画書 §3「変更内容」の各項目が実装されているか
- 計画書 §2.2「変更しないこと」に踏み込んでいないか
- §6「検証プラン」の各行を実際に実行できるか（書いただけになっていないか）

### G2 の判定

不合格にする条件:

- テストが落ちている（原因を特定できなければエスカレーション）
- 計画書に無い変更が混ざっており、必要性を説明できない
- 受け入れ条件を満たしていない

不合格なら**次のチェックリスト項目に進まない**。計画書を更新してから再委譲する
（設計判断はワーカーにさせない）。再委譲の上限は `doc/workflow.md` §3。

合格したら計画書のチェックリストを更新し、**実装系の項目がすべて完了していれば続けて G3 に進む**。

## G3: ブランチレビュー（ブランチ完了時・ユーザーの指示を待たずに実行）

### G3-1. 対象か判定する

```powershell
git diff --shortstat main..<branch>
```

`doc/workflow.md` §3「G3 の対象」で判定する。対象外なら、その理由（種別 D・閾値未満など）を
計画書 §6.3「レビュー記録」に1行書いて G3 を終える。

### G3-2. `/code-review` を実行する

Skill ツールで `code-review` を起動する。レベルは `doc/workflow.md` §3 に従う。

```
/code-review <level> main...<branch>
```

- `--fix` は付けない。修正は G3-3 の仕分けを経て、計画書の更新 → 再委譲の経路で行う。
- レビューはブランチ単位で行う。チェックリスト項目ごとには実行しない。

### G3-3. 指摘を仕分ける

**全指摘**を次の3区分に仕分け、計画書 §6.3「レビュー記録」に記録する。
**重大な指摘は件数に関係なく全件を仕分ける**（`doc/workflow.md` §3.1。件数を絞るのはユーザーへの報告だけ）。

| 仕分け | 条件 | 次の行動 |
| :--- | :--- | :--- |
| 対応 | このブランチの意図に関わる欠陥 | 計画書 §5 に修正項目を追加し、ワーカーに再委譲 → G2 |
| issue 化 | 実在するが本ブランチのスコープ外 | `doc/issue_list.md` に起票し、リンクを記録 |
| 却下 | 誤検出・意図どおり・テストで検出できる種類 | **理由を必ず書く** |

狙う欠陥の型（「実装もテストも通るが意図を満たしていない」）は `doc/workflow.md` §3.1。
仕分けで設計判断が必要になったら、エスカレーション条件2に該当する。

### G3-4. 再レビュー

「対応」が1件以上あれば、修正の G2 を通したあと G3-2 から繰り返す。
往復の上限は `doc/workflow.md` §3。上限を超えても未対応の重大指摘が残るならエスカレーションする。

### G3-5. merge 可能の報告

**G3 を通るまで「merge 可能」と報告しない**（merge 後にレビューした実例がある）。

## 完了報告に含めるもの

1. 変更ファイル一覧（パス＋変更概要）
2. テスト結果（passed / failed 数）
3. **変更種別 A〜D**（省略不可）
4. 受け入れ条件との照合結果（G2-4）
5. G3 の結果 — 指摘の総数と仕分けの内訳、**重大度つきの上位の指摘**（件数は `doc/workflow.md` §3「G3 のユーザー報告」）、全件は計画書 §6.3 にある旨。
   対象外ならその理由
6. ワークツリーの場合: ブランチ名・SHA・取り込みコマンド（`git diff main..<branch>` → `git merge <branch>`）
7. 未解決の課題・計画の穴
8. merge 後に必要な処理（種別 B / C なら G5 昇格。`doc/workflow.md` §1）
