---
description: ワーカーの成果物を検収する（動作の確認＋意図の確認の2段）
argument-hint: "[計画書パス]（省略時は doc/in_progress/ から推定）"
---

成果物を検収する。**検収なしで次のチェックリスト項目に進まない**（CLAUDE.md「サブエージェント委譲」）。

検収は2段ある。**1段目は「動くか」、2段目は「意図を満たすか」**で、目的が違う。
1段目だけでは、実装もテストも通るが意図を満たしていない欠陥が素通りする
（実例: WAL チェックポイントが「呼んでいるのに一度も効いていない」状態に誰も気づけなかった件）。

---

## 第1段: 動作の確認（全変更で必須）

### 1-1. 差分を読む

```powershell
git diff                      # 本体チェックアウトの場合
git diff main..<branch>       # ワークツリーの場合
```

**計画書に書かれていない変更が混ざっていないか**を最初に見る。混ざっていたら、
それが必要な変更なのか、ワーカーの逸脱なのかを判断する（逸脱なら計画書を更新してから受け入れる）。

### 1-2. テスト全体を実行する

```powershell
.\venv\Scripts\python.exe -m pytest backend/tests/ -q
```

対象ファイルに絞った実行はワーカー側で済んでいる。**ここでは全体を回す**
（他を壊していないことの確認が検収の目的）。フロントエンドに触れた場合は `cd frontend; npm test` も。

### 1-3. 変更種別を判定する

`doc/agent_execution_rules.md` §10.2 の4種別。**完了報告に必須記載**。

| 種別 | 例 | merge 後に必要な処理 |
| :--- | :--- | :--- |
| A: コードのみ | API・フロントエンド・バックテストロジック | なし |
| B: データ形状に触れる | スキーマ変更・indicator 追加・パイプライン変更 | データ昇格（`tools\deploy_after_merge.ps1`） |
| C: ユーザー資産 DB に触れる | `user_data.db` のスキーマ変更 | バックアップ＋in-place マイグレーション |
| D: 設定・ドキュメントのみ | CLAUDE.md・TOML・計画書 | なし |

---

## 第2段: 意図の確認

### 2-1. 受け入れ条件との照合（全変更で必須・追加コストなし）

第1段で読んだ差分を、**計画書の受け入れ条件と突き合わせる**。
「テストが通った」ではなく「**計画書が要求したことを、コードが実際に満たしているか**」を見る。

- 計画書 §3「変更内容」の各項目が実装されているか
- 計画書 §2.2「変更しないこと」に踏み込んでいないか
- §6「検証プラン」の各行を実際に実行できるか（書いただけになっていないか）

### 2-2. コードレビュー（対象を限定して実施）

`/code-review` を **ブランチ単位で1回**実行する。チェックリスト項目ごとには実行しない
（コンテキスト再構築コストで割高になり、CLAUDE.md の粒度指針にも反する）。

#### 対象

| 変更種別 | レビュー |
| :--- | :--- |
| **B（データ形状）・C（ユーザー資産 DB）** | **必須**。事故が起きているのはこの層で、merge 後の昇格が絡むと巻き戻しコストが跳ね上がる |
| **A（コードのみ）で差分が大きいもの** | **必須**。閾値は下記 |
| A（コードのみ）で小さいもの | 任意。2-1 の照合で足りる |
| D（設定・ドキュメント） | **不要**。巻き戻しが容易 |

#### 種別 A の閾値

**変更行数 200行 または 変更ファイル 5本を超えたら**レビュー対象とする。

> [!NOTE]
> **この数値に根拠はない。運用しながら調整する前提の暫定値である**（2026-09-10 設定）。
> 「レビューが多すぎて読まれない」「大きい変更が素通りした」のどちらかが起きたら見直すこと。
> 数字を動かした場合は、CLAUDE.md 側の記述も併せて直す（定義箇所は2箇所ある）。

確認方法:

```powershell
git diff --shortstat main..<branch>
```

#### 出力の縛り 🔴

レビュー結果は次の形に絞らせる。**絞らないと形骸化する。**

- **上位3件まで**
- **重大度つき**
- **テストで検出できない種類に限る**（lint・型・テストが拾えるものは対象外）

10件の些細な指摘を返すレビュアーは数週間で読まれなくなり、
`doc/issue_list.md` P3 に書いたとおり**無いより悪い**（読んだ人が古い・些末な指摘で判断する）。

#### 何を見つけたいのか

**実装もテストも通るが、意図を満たしていない**型の欠陥。テストでは落ちない。

- 呼んでいるが効いていない（戻り値・副作用を確認していない）
- 仕様書の記述と実装がずれている（`doc/backend_specification.md` 等との照合）
- 既存の共通関数を再実装している（例: スクリーナー特殊フィルタは
  `indicators/screener_filters.py` がバックテストと共用。SQL で再実装してはいけない）
- 隔離の前提を壊している（本番パス直書き・sandbox を経由しない書き込み）

---

## 完了報告に含めるもの

1. 変更ファイル一覧（パス＋変更概要）
2. テスト結果（passed / failed 数）
3. **変更種別 A〜D**（§10.2。merge 後の処理が変わるため省略不可）
4. 受け入れ条件との照合結果（2-1）
5. レビューを実施した場合はその結果、**実施しなかった場合はその理由**（種別 D・閾値未満など）
6. 未解決の課題・計画の穴

## 検収で不合格にする条件

- テストが落ちている（原因を特定して修正するか、ユーザーに報告して判断を仰ぐ）
- 計画書に無い変更が混ざっており、必要性を説明できない
- レビューが必須の種別なのに実施していない

不合格の場合は**次のチェックリスト項目に進まない**。計画書を更新してから再委譲する
（設計判断はワーカーにさせない）。
