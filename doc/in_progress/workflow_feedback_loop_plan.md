## 3. 変更内容

### 3-A. `.claude/commands/` の新設

- **何を**: 3つのコマンドを作る。
  - `/start-item <名前>` — テンプレートを `doc/in_progress/<名前>_plan.md` にコピーし、
    §1〜§5 の記入と §4 のユーザーレビューまで誘導する（rules §9 の手順そのもの）
  - `/accept` — 検収。①`git diff` の確認 ②テスト全体実行 ③**計画書の受け入れ条件との照合**
    ④変更種別 A〜D の判定と完了報告への記載
  - `/cleanup` — 棚卸しと撤収。`tools/check_worktrees.ps1` を実行し、
    出力に応じて `tools/remove_worktree.ps1` を案内する
- **なぜ**: これらは現在 CLAUDE.md の散文にしかなく、毎回手順を組み立て直している。
  先行計画で撤収漏れが13本たまっていたのは、**撤収手順が明文化されていなかった**ことの帰結。
- **影響範囲**: エージェントの手順のみ。コード・データに影響なし。

### 3-B. 種別 B / C に限定したエージェント側レビュー

- **何を**: 検収を2段にする。
  - **全種別**: 現行どおり `git diff` 確認＋テスト全体実行（＝動くか）
  - **種別 B / C、および差分の大きい種別 A**: merge 前に `/code-review` を**ブランチ単位で1回**（＝意図を満たすか）
- **出力の縛り**: **上位3件まで・重大度付き・テストで検出できない種類に限る**。
  10件の些細な指摘を返すレビュアーは数週間で読まれなくなり、
  P3 でユーザー自身が書いているとおり**無いより悪い**。
- **なぜ B / C に限定するか**: 事故が起きているのはこの層で、merge 後の昇格が絡むと
  巻き戻しコストが跳ね上がる。種別 D（設定・ドキュメント）は巻き戻しが容易なので対象外。
- **狙う欠陥の型**: WAL チェックポイントが「**呼んでいるのに一度も効いていない**」状態に
  誰も気づけなかった件（`doc/issue_list.md` 記載）のような、
  **実装もテストも通るが意図を満たしていない**もの。テストでは落ちない。
- **対象**: CLAUDE.md「サブエージェント委譲」節、`.claude/commands/accept.md`

### 3-C. PostToolUse による対応テスト実行

- **何を**: `backend/**.py` を編集したら、対応するテストファイルだけを実行して結果を報告する。
- **対応テストの解決**: `backend/x/y.py` → `backend/tests/x/test_y.py`。
  無ければ同名 `test_y.py` を `backend/tests/` 配下から探す（現行の 1:1 ミラー規約に従う）。
- 🔴 **テストが無い場合こそ報告する**: 138モジュール中 **86 に対応テストが無い**。
  「テストが無い→黙って何もしない」にすると、**ゲートを敷いた実感だけが残って実際は沈黙する**。
  「このモジュールには対応テストが無い」と明示的に出す。
- **失敗してもブロックしない**: 報告のみ。TDD の red フェーズを書けなくするため deny にはしない。
- **対象**: `.claude/settings.json`（PostToolUse を追加）、`tools/hooks/run_related_tests.ps1`（新規）
- **注意**: フックのスクリプトは **ASCII のみ**（PowerShell 5.1 の CP932 誤読対策。
  `git_guard.ps1` / `check_worktrees.ps1` と同じ規約）。
  stdout の扱いはフックの契約に従う（`git_guard.ps1` の実装を参照）。

### 6.1 反証 — この結論が誤りだとしたら、何が観測されるはずか

- **この結論が誤りだとしたら観測されるはず**:
  本計画の前提は「**既存手順に1段足すだけで見返しが機能する**」。誤りなら次が観測される。
  - **形骸化**: コマンドが数週間で使われなくなる／レビュー指摘が読み飛ばされる。
    → 観測方法: `/accept` を経由した検収の回数と、`git_guard.ps1` のログに残る git 操作の回数を比べる。
    乖離が大きければコマンドが迂回されている。
  - **沈黙**: PostToolUse が「対応テスト無し」ばかり返し、実質何も検出しない。
    → **86 / 138 という比率から、これは十分起こりうる**。1週間運用して
    「テストが走った回数」対「無しと報告された回数」を数える。後者が大半なら、
    **本当の欠陥は L1（テスト充足率）であって、ゲートを敷いても解決しない**ことになる。
  - **誤検出**: レビューが毎回3件を埋めるために些細な指摘を返す。
    → 指摘のうち実際に修正へ至った割合を見る。低ければ「上位3件」という枠自体が誤り。
- **独立経路での確認（実施済み 2026-09-10）**:
  3件のうち「**沈黙**」は着手前に測れるため、**git 履歴という独立経路**で実測した
  （エージェントの自己申告ではなく、実際に行われた編集の記録）。
  直近150コミットの `backend/*.py` 編集イベント120件について、
  対応テストが今日時点で存在するかを判定した。

  | | 件数 | 割合 |
  | :--- | ---: | ---: |
  | テストがあるモジュールの編集（ゲートが走る） | 62 | **52%** |
  | テストが無いモジュールの編集（「テスト無し」報告） | 58 | 48% |

  **予測は外れた。** 静的な比率（86 / 138 = 62% がテスト無し）から「大半が沈黙する」と
  予測したが、**編集頻度で重み付けすると 48% に下がる**。
  テストの無い86モジュールの多くは**そもそも誰も触らないファイル**（使い捨てスクリプト等）で、
  よく編集されるモジュールは相対的にテストが厚い。
  **静的な比率で語ったのが誤りだった**（カルテ第2版で L1 を下げた根拠も同じ静的比率であり、
  「86 / 138」は充足率の指標としては正しいが、**ゲートの有効性の指標としては誤用**だった）。

  → 結論: 本計画の前提「既存手順に1段足すだけで見返しが機能する」は、
  少なくとも 3-C については**維持できる**。約半分の編集で実際にテストが走る。

  **副産物 — L1 の急所が特定できた**。「テスト無し」かつ編集頻度の高いファイル:

  | 編集回数 | ファイル |
  | ---: | :--- |
  | 6 | `backend/api/screener_router.py` |
  | 6 | `backend/api/chart_router.py` |
  | 4 | `backend/backtest/backtest_runner.py` |
  | 4 | `backend/backtest/backtest_screener.py` |
  | 4 | `backend/api/schemas.py` |
  | 3 | `backend/pipeline/parquet_maintenance.py` |
  | 3 | `backend/db/models.py` |

  **「86モジュールにテストが無い」より、この7本のほうが行動可能な情報**である。
  router 層が集中的に無防備だと分かった（§8 に送る）。

- **残り2件（形骸化・誤検出）は運用データが要るため未実施**。
  これらは `logs/git_guard.log` と PostToolUse の実行結果で判定する。
  **ただし「後で測る」は契機が無ければ実施されない**（P3 で自ら書いた形骸化の型そのもの）。
  §8 に残すだけでなく、**`/cleanup` の棚卸し項目に含めて契機を作る**こと。
