## 1. 背景と目的

### 現状の問題

`is_rs_blue_dot` / `is_rs_red_dot`（`backend/indicators/relative_strength.py` L79-96）は
**その日の状態を表す 0/1 フラグ**で、スクリーナーは `bool_column` として
**基準日1行だけ**を評価する（`backend/indicators/screener_registry.py` L376-380）。
つまり **点灯した当日しかヒットしない**。

これは指標の本来の使い方と合っていない。ブルードットは「ベース（浅い調整）形成中に
RS ラインが先に新高値を付ける」という**先行シグナル**であり、実際の買いは数日〜数週間後の
ピボット上抜けで判断する **2段構え**の指標である。当日フラグではこの運用が表現できない。

実害も出ている。`G3_bluedot_leader` は `max_hits_per_day = 10` に対して点灯率が
**約 0.36%/日**（`backtest_config.toml` L555 のコメント）しかなく、枠が埋まらない
＝最適化で「枠遊び」が起きる。

### 目的

`is_rs_blue_dot` / `is_rs_red_dot` を **経過日数カラムへ仕様変更**し、
「点灯から N 日以内」という窓をスクリーナー側の閾値で切れるようにする。
これにより **N が Optuna の int パラメータになる**（現在は窓という概念自体が無い）。

> [!IMPORTANT]
> **目的の再定義（2026-08-29・Phase 0 の実測とユーザー判断を受けて）**
>
> 当初の目的は「G3 の検出件数を増やして枠遊びを解消する」だったが、実測（§7.1 / §7.1b）で
> 窓を広げても `avg_gain` は改善しないことが判明した。一方で **勝率・大負け率の観点では
> 一貫した効果があり、それはベース離脱型トリガーとの2段構えで再現する**。
>
> したがって本計画の目的を次に置き換える:
>
> **ブルードットは一般に確立された指標であり、本来の用法は「ウォッチリスト昇格の資格」で
> あってエントリーシグナルではない。現在のプロジェクトの使い方（当日フラグ単発）が
> 本来の用法と食い違っているので、それを正す。** 窓化は「件数を増やすため」ではなく
> **「2段構えを表現できるようにするため」**に行う（現行フラグでは E1/E4 との交差が
> 3.2件/日・0.45件/日しかなく、戦略として組めない）。
>
> 採否の評価軸も `avg_gain` 単独ではなく、**リスク調整後（MaxDD・大負け率）**を併せて見る。

### 成功条件

- `rs_blue_dot_age` / `rs_red_dot_age` が T3 の正式カラムとして SQLite・Parquet の**全期間**に存在する
- スクリーナー・型1バックテスト・型3シナリオの3経路で `min_` / `max_` フィルタとして評価できる
- `G3_bluedot_leader` の窓 N を Optuna が振れる状態になり、検出件数が枠に見合う水準になる
- **フィルタ層のコード改修がゼロで済む**（numeric 経路に自動で乗る）

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 | 理由 |
| :--- | :--- | :--- |
| 符号1列（TD9 方式：正=ブルー / 負=レッド） | **採らない。2列に分ける** | **レッド除外窓が列生成時に固定され Optuna で振れない**。`min_rs_dot_seq >= -5` は「直近レッド(-1〜-5)を通して古いレッドを弾く」という意図と真逆の動作になり、除外窓の長さを閾値で表現する手段が構造的に無い。ブルー側も `min_=1` と `max_=N` の**2条件必須**になり、`min_` の書き忘れが「未点灯の全銘柄が通る」サイレント素通しになる。2列なら `max_rs_blue_dot_age = 10` / `min_rs_red_dot_age = 20` の**各1条件**で書け、両方が Optuna の探索対象になる |
| 未点灯を NULL にする | **採らない。番兵 999 を入れる** | numeric フィルタは NaN 比較が全て False になるため、`min_rs_red_dot_age = 20` で**未点灯銘柄まで除外される**逆転バグになる。「常に値を持たせる」判断（ユーザー提案）が正しい |
| 列名を据え置いて意味だけ変更 | **採らない。必ず改名する** | `0` の意味が「非点灯」→「当日点灯」に**反転**する。`chart_router.py` L457 の `bool_or_none` は `bool(0)=False` なので**点灯日が False・未点灯が True** になる。改名すれば参照箇所は Python の AttributeError / TS の型エラー / `UnknownFilterKeyError` で**必ず落ちる**ため、移行漏れを機械的に検出できる |
| カウンタに上限を設けない | **採らない。上限 N で 999 に飽和させる** | **調査で判明**: T3 の日次計算は SQLite から**全行を読んで全期間を再計算**する（`pipeline/phases/t3_indicators.py` L22-33）が、ホットキャッシュは**730日しか保持していない**。252日のウォームアップを引くと実効窓は約 478 本で、上限なしのカウンタは窓端で切れて Parquet 側の値と食い違う。**「上限で解除する」というユーザーの当初案が正しかった** |
| 騙し無効化（50SMA 割れ・構造 HL 割れ）を列に埋める | **初版では埋めない。Phase 0 の実測後に再判断** | 「今 50SMA より上」は当日条件なので既存の `is_close_gt_sma50` で書けて、Optuna が on/off も閾値も振れる。列に埋めると**ガードあり/なしの A/B ができなくなる**。既に G3 は `is_close_gt_sma50` を `categorical = [true]` として最適化対象に置いており、ガードを固定側へ移すのは既存の設計思想と逆行する。ただし**単独使用時の暴発を列が防がない**という弱点は実在するため、§6.0 の実測で判断材料を取る |
| T4（相対ランク）への追加 | **しない** | 経過日数の横断パーセンタイルに意味が無い |
| ショート戦略への展開 | **やらない** | レッドドットは**除外フィルタとしての利用**が目的 |

## 3. 変更内容

### 3.1 カラム定義

| カラム | 型 | 内容 |
| :--- | :--- | :--- |
| `rs_blue_dot_age` | SMALLINT NOT NULL | `0`=当日点灯 / `n`=n営業日前に点灯 / `999`=未点灯・無効 |
| `rs_red_dot_age` | SMALLINT NOT NULL | 同上（レッドドット） |

**生成規則**:

1. 点灯日に `0`、翌営業日以降 `+1`
2. **上限 N（既定 60）を超えたら `999`**（＝「十分昔」と「一度も点灯していない」を同じ値に統合する）
3. **反対ドットが点灯したら即 `999`**（ブルーをカウント中にレッドが点いたらブルーは無効。逆も同様）
4. 再点灯したら `0` に戻す（「直近点灯からの経過」という意味を保つ）
5. **利用可能な履歴が 252 本未満の行は `999`**（`rolling(252, min_periods=1)` 由来の偽点灯を止める）

> [!IMPORTANT]
> **Optuna の探索範囲は `1 .. N-1` に収めること。** N を超える閾値は
> 「N日以上前」も `999` に潰れているため意味を持たない（`min_rs_red_dot_age = 90` は
> 61〜89日前に点灯した銘柄も通してしまう）。N の既定値は Phase 0 の実測を見て確定する。

実装は `td9` と同じ njit カーネル（`indicators/volatility.py` L7-19）の形に揃える。
反対ドットによる無効化があるため cumsum では書けず、逐次ループが素直。

### 3.2 T3 計算

`indicators/relative_strength.py::calc_relative_strength()` の L79-96 をカウンタに差し替える。
`df_spy` が無い場合の早期リターン（L13-16）も `999` を入れる形に直す。

**あわせて既存の潜在不整合を直す**: `pipeline/phases/t3_indicators.py` L112 と
`backend/scripts/weekly_maintenance.py` L426 の dtype キャスト対象リストは
`'rs_blue_dot'` / `'rs_red_dot'` という**旧名のまま**で、実際のカラム名 `is_rs_blue_dot` と
一致していない。**現状このキャストは発火していない。** 新カラム名を正しく登録する。

### 3.3 スクリーナー / バックテスト

**コード改修は不要。** `rs_blue_dot_age` は `is_` 接頭辞を持たないため、
`min_` / `max_` の numeric 経路（`screener_registry.py` L365-373）で自動的に解決される。
スクリーナー・バックテスト・Optuna の3経路が同時に対応する。

削除により `is_rs_blue_dot = true` を書いた既存設定は `UnknownFilterKeyError` で落ちる（意図通り）。

## 7. 途中発生した課題

### 7.1 Phase 0 の実測により、本計画の前提が否定された（2026-08-29）

**事象**: §6.0 の実測で、本計画の中核仮説「ブルードットは先行シグナルなので、
点灯後の数日〜数週間の窓で拾えばよい」が支持されなかった。

**根拠**:

1. **窓を広げても改善しない。むしろ悪化する。** ベース条件7種すべてで、
   `max_rs_blue_dot_age <= k` の上乗せ増分は `k` が大きいほど検証期で悪化した
   （G3相当で k=3/5/10 → -0.75 / -1.07 / -1.41pp）。
   価値らしきものは**点灯当日に集中し、翌日以降は残らない**。
2. **`blue_age <= 0`（＝現行の当日フラグ）が最良**だった。ただしその超過も
   +0.04〜+0.12pp（SE ±0.15）でゼロと区別できない。
3. **レッド除外は機能しない**（±0.02pp）。加えて反対ドット無効化を列に入れると
   レッド列はブルー窓と併用時に冗長になる（B-3）。

**結論**: **T3 カラム化を実施しない**。スキーマ変更・Parquet 全期間バックフィル・
本番昇格（数時間規模）を行っても、得られるのは「ゼロと区別できない当日フラグ」の
言い換えでしかない。**実測を列作成の前に置いた設計判断（Phase 0 を先頭に置いたこと）が
そのままコスト回避になった。**

**留保**: 評価は 20営業日・-8%ストップ付きフォワードリターン（型1目的関数 `avg_gain`
の代理）という単一指標に基づく。型3（有限資産・コストあり）で違う結論が出る可能性は
残るが、**型1の最適化を回しても改善が期待できない**以上、先に型3へ進む理由が無い。

### 7.1b 追加実測により §7.1 の結論を修正（2026-08-29・ユーザー指摘を受けて）

**指摘**: (1) C群は平均リターンしか見ておらず「ハズレの除外」＝勝率・下振れの観点が抜けている。
(2) この指標の本来の用途は**ウォッチリスト昇格の資格**であり、エントリーは別トリガーで取る
**2段構え**である。C群はそれを測っていない。

両方とも妥当だったため `tmp/probe_rs_dot_watchlist.py` で測り直した。

**修正点1 — 勝率では一貫して効いている（C群の再読）**:

| 条件 | 学習 勝率 | 検証 勝率 | ヌル比 |
| :--- | ---: | ---: | :--- |
| 母集団（ヌル） | 45.1% | 47.4% | — |
| `blue_age <= 0` | 49.2% | 51.4% | **+4.1 / +4.0pp** |
| `blue_age <= 5` | 47.9% | 50.4% | +2.8 / +3.0pp |
| `blue_age <= 20` | 47.4% | 49.5% | +2.3 / +2.1pp |

**両期間で一貫して正**。平均超過がほぼゼロなのに勝率が +4pp ＝
**「勝ちやすいが勝ち幅が小さい」**（高値圏で買うので上値余地が限定的）。
`avg_gain` 主軸の評価ではこの性質は捕まらない。

**修正点2 — 2段構えでは、トリガー依存で「大負けの除外」が再現する**（保有20日、対照は同じ
トリガーの `blue_age == 999` ＝未点灯群）:

| トリガー | 群 | 学習 勝率 / 大負率 | 検証 勝率 / 大負率 | 件/日 |
| :--- | :--- | ---: | ---: | ---: |
| E1 構造ピボット上抜け | +blue<=10 | 48.0 / **33.3** | 48.9 / 34.4 | 4.5 / 3.5 |
| | 未点灯（対照） | 44.7 / 36.2 | 47.1 / 34.7 | 63 / 75 |
| E3 63日高値更新 | +blue<=10 | 47.5 / 27.9 | 49.5 / 28.7 | 13.5 / 12.3 |
| | 未点灯（対照） | 48.7 / **24.1** | 49.5 / **25.4** | 79 / 93 |
| E4 VCP収縮＋ピボット上抜け | +blue<=20 | 47.3 / **23.1** | 54.3 / **21.1** | 0.47 / 0.45 |
| | 未点灯（対照） | 41.3 / 39.8 | 52.4 / 30.8 | 10.4 / 13.5 |

- **E4（最も収縮の効いたセットアップ）で効果が最大**。大負率（-8%ストップ到達率）が
  **-16.7pp / -9.7pp**、勝率 +6.0 / +1.9pp と**両期間で再現**する
- **E1 は学習期のみ**（勝率 +3.3 / +1.8pp、大負率 -2.9 / -0.3pp）。検証期は弱い
- **E3（単なる高値更新）は逆効果** — 大負率がむしろ上がる。ブルードットと情報が重複しており、
  組み合わせるトリガーを選ぶ
- **どのトリガーでも平均超過リターンは改善しない**。負けを減らすと同時に勝ちも減らしている

**修正後の結論**: §7.1 の「価値なし」は言い過ぎだった。正しくは
**「`avg_gain` 主軸の型1では価値が出ないが、リスク調整（大負けの除外）の観点では
トリガー次第で再現性のある効果がある」**。

**窓化そのものを支持する材料も出た**: E1/E4 と `blue_age <= 0`（現行フラグ）の交差は
件数が薄すぎて戦略として成立しない（E1+blue<=5 で 3.2件/日、E4+blue<=20 で 0.45件/日）。
**2段構えを組むには窓が必須**である。

**次の一手（§8 へ）**: 列を作る前に、**簡易ポートフォリオシミュレーション（有限枠・
コストあり・MaxDD 計測）を probe で回し、窓の有無でリスク調整後の成績が改善するか**を見る。
改善すれば Phase 1 へ進み、しなければ中止する。Phase 0 の思想（作る前に測る）の延長。

### 7.1c 有限枠ポートフォリオでの検証（2026-08-29）

`tmp/probe_rs_dot_portfolio.py`。枠 10/5、保有 20/60 日、-8% ストップ、コスト片道 0.05%。
枠超過時の選抜は**流動性順**（リターン予測力を持たない中立ルール）。
**対照群として同じトリガーの `blue_age == 999`（未点灯）を必ず並べた** — これが効果を
「ブルードットによるもの」と「単に件数が減ったこと」に切り分ける統制になる。

**主結果（枠10 / 保有20日）**:

| トリガー | 腕 | 学習 損切% / Calmar | 検証 損切% / Calmar | 稼働% |
| :--- | :--- | ---: | ---: | ---: |
| **E4 VCP収縮＋上抜け** | 単独 | 38.6 / -0.32 | 37.6 / 0.41 | 90 |
| | **+blue≤10** | **24.4 / +0.23** | **30.2 / 0.45** | 19-20 |
| | 未点灯（対照） | 41.6 / -0.29 | 40.6 / — | 88 |
| E1 構造ピボット上抜け | 単独 | 33.6 / -0.07 | 26.8 / 0.59 | 94 |
| | +blue≤10 | 27.2 / +0.26 | **33.7 / -0.19** | 85 |
| | 未点灯（対照） | 34.3 / +0.50 | 29.6 / 0.12 | 94 |

**確認できたこと（再現性あり）**:

1. **E4（収縮を伴うセットアップ）では、ブルードット窓が損切率を両期間・全設定で下げる**
   （枠10/20日 -14.2 / -7.4pp、枠10/60日 -4.6 / -17.5pp、枠5/20日 -16.1 / -4.5pp）
2. **同組み合わせで Calmar が両期間で改善**（学習 -0.32 → +0.23、検証 0.41 → 0.45）
3. **未点灯対照群はトリガー単独とほぼ同じ成績** ＝ 効果はブルードットに由来しており、
   単に件数が減ったことの副産物ではない。**この統制が最も重要な確認事項**

**確認できなかったこと・限界**:

1. **E1（収縮条件なし）では一貫しない** — 学習で改善、検証で逆転する。
   相性の良いトリガーは「収縮を伴うセットアップ」に限られる
2. **稼働率が 19〜20% しかない** — MaxDD の低さはキャッシュ比率の高さに一部起因する。
   腕ごとに露出量が違うため CAGR / MaxDD の直接比較には注意が要る
3. 取引数 63〜86 件と少なく、CAGR の推定誤差が大きい

**解釈**: 「収縮したベースの中で RS が先行して新高値を付け、その後ベースを上抜ける」という
教科書どおりの並びでのみ効果が出た。理屈と実測が一致している。

**判断**: **Phase 1（列化）へ進む。** 現行の当日フラグでは E4 との交差が 0.45件/日しかなく
この2段構えを戦略として書けない。窓化は「本来の用法を表現可能にする」ために必要。
