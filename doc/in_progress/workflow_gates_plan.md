## 1. 背景と目的

2026-09-23 のワークフロー見直しで、ユーザーが次の4点を優先項目とした。

1. **③ 検収のコードレビューをエージェントだけで回せるようにする**（人のレビューは merge 時に別途ある）
2. **ハーネス1** — 同じ規則・数値が複数箇所に定義され、食い違いも出ている
3. **ハーネス2** — CLAUDE.md の肥大化（整理を含む）
4. **ループ3** — ユーザーが介入する地点が明文化されていない

4つとも根は同じで、**ワークフローの「ゲート」（通過条件つきの関門）が文書に散らばっていて、ゲートごとに誰が判断するのかが定義されていない**。
個別に直すと同じ文書を3回書き換えることになり、また散らばる。
そこで**ゲート表を1枚作り、ほかの文書はそこから派生させる**。

**エスカレーション条件**（どのゲートでも、該当したら止めてユーザーに上げる）

### 3-B. `/accept` の G3 自動化

- **起動契機**: 計画書 §5 の実装系チェック項目がすべて完了し、G2 を通過した時点で、ユーザーの指示を待たずに実行する。対象（種別 B / C、閾値超えの A）でなければ、スキップ理由を記録する。
- **実行**: Skill で `code-review` を起動する（対象は `main...<branch>`）。
  - レベルは種別 B / C が `high`、種別 A が `medium`（§4-4）。
- **仕分け**: オーケストレーターが全指摘を3区分する。
  - **対応**（計画書を更新して再委譲）
  - **issue 化**（`doc/issue_list.md`）
  - **却下**（理由つき）
- **重大な指摘は件数に関係なく全件を仕分ける**（§4-2）。「上位3件」は**ユーザーへの報告**の上限と再定義する。
- **ループ**: 対応した指摘があれば再レビューする。上限2周を超えたらエスカレーションする。
- **記録**: 全指摘と仕分け結果を計画書の「レビュー記録」欄に残す。G4 の人レビューと、P3 の効果測定の材料になる。
- **順序の保証**: G3 を通るまで「merge 可能」と報告しない（split_aware で起きた merge 後の実行を防ぐ）。

### 3-C. 介入地点の明文化

- ユーザーが判断するのは **G1 / G4 / G5 とエスカレーション条件だけ**とする。
- 次の作業は**ユーザーに聞かずに進める**。
  - G2 / G3 の実行
  - レビュー指摘の仕分けと再委譲
  - 計画書の更新・記録
- G6 は「ユーザーの指示で、エージェントが実行」に統一する（§7 と `/cleanup` の矛盾を解消）。

### 3-D. `agent_execution_rules.md` の参照化

- 更新履歴に「何の事故を防ぐためか」を1行で記録する（P3 の提案に沿う）。

### 3-E. コマンドとワーカー定義
