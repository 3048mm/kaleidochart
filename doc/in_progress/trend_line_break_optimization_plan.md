## 1. 背景と目的

`is_structure_trend_line_break`（作者の `rt_cnt_break`）は 2026-08-29 に実装・本番昇格したが、
**スクリーン条件としての採否検証（バックテストで edge があるか）は未実施**のまま残っている。
`data/optimization_trials.db` の全81 study を確認したが、TLB を使った study は1本も無く、
`backtest_config.toml` にも該当する `[[strategy]]` 定義が無い。

現在 TLB は「観察用途」として Check 相当に置かれているだけで、**Pickup（実運用のスクリーン条件）に
格上げできるかの根拠が無い**。本タスクはその根拠を出す。採用・不採用のどちらでも成果とする。

### ここが H1 と決定的に違う

§5.3 で H系が全滅した真因は**検出件数不足による枠遊び**だった
（`H1_structure_pivot_ready` は 0.29件/日 で、検出件数ゲート下限 0.3件/日 を下回っていた）。

**TLB は問題が正反対で、生では 26件/日 と過剰に出る。** H1 相当の条件を乗せた地点で
2.2〜3.2件/日 に落ち着き、**両学習期間ともゲート帯（下限 0.3 / 上限 5.0）の内側**に入る。

したがって本タスクの論点は「枠が埋まらない」ではなく **「多すぎる候補から何で選ぶか」** になる。
`max_hits_per_day` が実効的に効くので、`sort_column` の選択が H1 より重い意味を持つ。

### 成功条件

型1バックテストの Alpha・LCB・AvgGain を既存戦略（特に E1 / E2 / B系）と並べ、
**採用水準に届くか届かないかを数値で確定させる**こと。届かない場合は §5.3 と同じ形式で
「不採用」と根拠を記録し、TLB は Check 用途のままとする。

### 3.1 戦略定義（`backend/backtest/backtest_config.toml`）

```toml
[[strategy]]
name = "H3_structure_trend_line_break"
description = "構造が無い期間のカウンタートレンド線を上抜けた転換シグナル"

# 流動性床は [general] が全戦略へ実行時注入するため戦略側には書かない

[strategy.optimization]
min_adr_pct_21     = { type = "float", min = 2.0, max = 7.0, step = 0.5 }
min_rs_trend_s21   = { type = "float", min = 0.90, max = 1.15, step = 0.025 }
min_dist_21ema_pct = { type = "float", min = -3.0, max = 5.0, step = 0.5 }
max_vcr            = { type = "float", min = 0.6, max = 1.5, step = 0.05 }
max_sma50_atr_mult = { type = "float", min = 3.0, max = 10.0, step = 0.5 }
min_market_cap     = { type = "categorical", choices = [1e8, 3e8, 1e9, 3e9] }
```

**ベースライン（トライアル0 に enqueue される既定値）は 2.24件/日**でゲート帯の内側。
`enqueue_baseline_trial` が最初に評価するので、探索が始まる前に地に足の着いた基準点が入る。

設計の意図:

- **`min_avg_hits_per_day` / `quality_gate_min_hits_per_day` は書かない。**
  グローバル既定（1.0 / 0.3）で足りる。H1 が抱えていた「下限を割る」問題が TLB には無い
- **`max_vcr` の上限を 1.5 まで伸ばす**のは「収縮を要求しない」状態を探索空間に含めるため。
  最強の絞り込み条件なので、効くなら 0.6〜0.8 側へ TPE が寄る。効かないなら 1.5 に張り付く
- **`min_dist_21ema_pct` の下限を -3.0 にする**のは TLB の性格上の判断。
  TLB は「構造が成立していない＝直近が弱い」期間に出るシグナルなので、
  21EMA より下で点灯するのが自然な形。H1 の 0.0 下限をそのまま使うと本来の母集団を切り落とす
- `max_allowed_dd` は書かない（2026-08-23 以降スコアから削除済みで未使用）

### Q4 の含意 — 単独での二値判定はしない

> **REV**: 「不採用という判断自体しないと思う。他と組み合わせてから評価するだろうし。」

これは §6 の判定基準の枠組み自体を変える。当初案は §5.3 の H1 と同じ
「Alpha > 0 なら採用 / 下回れば不採用」という二値判定だったが、**採らない**。

理由: TLB は構造が成立していない期間にだけ点灯する（`sp_pivot` と排他）ため、
既存戦略とは**母集団が重ならない**。単独スクリーンとして E1/E2/B系 と同じ土俵に
並べても、勝ち負けが「組み合わせたときの寄与」を代表しない。

**本タスクの成果物は「単独 study の best パラメータ1組」ではなく、
「どのパラメータ帯で期待値が正になるか」の地図とする。** §6 参照。

### `min_market_cap` について

> **REV**: 「market_cap は含めてね。数の調整で必要になるケースが経験則的に多いので。」

§1 の実測では効きが弱い（$2M 流動性床の上で 3e8 → 25.73件/日、1e9 → 22.11件/日）が、
**探索空間には含める**。理由は経験則どおり「検出件数の微調整に使える枠」であること。
本件は候補が 26件/日 と過剰で `max_hits_per_day` の枠が実効的に効くため、
他の条件で削りすぎたときに件数を戻す方向の自由度として意味がある。

選択肢は `[1e8, 3e8, 1e9, 3e9]` の4段階（§3.1）。

## 6. 検証プラン / 結果

### 6.1 何を出すか

Q4 の判断により、**単独スクリーンとしての採否は判定しない**。代わりに次の3点を残す。

1. **パラメータ帯の地図** — 200トライアルの全結果から、`expectancy_lcb > 0` を満たす
   トライアルがどのパラメータ領域に集まるかを集計する。「best 1組」だけでは
   組み合わせ検討の材料にならないため、上位帯の分布を表にする
2. **TLB 単独の素の実力** — Alpha / LCB / AvgGain / 勝率 / 件/日 を既存戦略と並べる。
   ただしこれは**性格の把握が目的**で、合否ではない（母集団が重ならないため）
3. **どの条件と相性が良いか** — 効きの強い `max_vcr` / `min_adr_pct_21` /
   `min_rs_trend_s21` について、正のスコアを出すトライアルがどちら側に寄るかを見る。
   これが「他と組み合わせる」際の出発点になる

#### 3. 相性 — `max_vcr` は「検出ゲートに阻まれたエッジ」

| `max_vcr` | 件数 | スコア中央値 |
| ---: | ---: | ---: |
| 0.80 | 8 | **-100.08**（罰点） |
| 0.85 | 36 | +0.365 |
| **0.90** | **54** | **+0.576** |
| 0.95 | 34 | +0.537 |
| 1.00 | 11 | +0.167 |
| 1.10 | 4 | -0.430 |

**最適値 0.90 は、検出件数ゲートを割る死に領域（0.85未満）のすぐ上。**
TPE は「ゲートに引っかからない範囲でできる限り収縮を要求する」方向に寄せている。
つまり**収縮（VCP 的な状態）との組み合わせは実エッジだが、検出件数が足りずに
それ以上締められない**。§5.3 で H 系を全滅させた「枠遊び」と同じ緊張が、
別の形で効いている。

検出件数とスコアの関係も同じことを示す:

| 件/日 | 件数 | スコア中央値 | AvgGain 中央値 |
| :--- | ---: | ---: | ---: |
| 0.3〜0.5 | 72 | **+0.576** | +2.78% |
| 0.5〜0.8 | 60 | +0.466 | +2.45% |
| 0.8〜1.2 | 14 | -0.108 | +1.49% |
| 1.2〜2.0 | 10 | -0.430 | +0.81% |
| 2.0〜 | 6 | -1.292 | -0.14% |

**緩めるほど単調に劣化する。** ベースライン（2.0件/日・AvgGain -0.67%）が弱かったのは
条件が緩すぎたためで、0.3〜0.5件/日 に絞ると +2.8% まで上がる。

#### 総括（採否の二値判定はしない — §4-Q4）

- TLB には**実エッジがある**。Alpha +2.87% は E2 を超え、H1 とは別物
- ただし**単独では推奨できない**。勝率 25.9% / LCB 負 / 最大DD -141% は、
  1トレードあたりの信頼性が低く裾に依存していることを意味する
- **組み合わせの方向は 2つ見えている**:
  1. **収縮（`max_vcr` 0.85〜0.95）** — 実エッジだが検出件数がボトルネック。
     TLB 以外の緩い条件と組み合わせて件数を確保できれば、もっと締められる
  2. **相場つき** — V字反発局面に強く、じり安相場に弱い。
     MTS（Market Trend Score）連動の型3で評価する価値がある
- **境界張り付きの真因は「範囲の狭さ」ではなく「検出件数ゲート」だった**（§7-5 で訂正）。
  `min_adr_pct_21` と `max_vcr` はどちらも**もっと締めたいがゲートに阻まれている**。
  → ゲートを開けた H3b で「締めるほど質が上がり続けるか」を確認する（実行中）


## 7. 途中発生した課題

### 7-1. ワークツリーでは `--mode read` では起動できない

`optimization_runner.main()` は冒頭で `init_db(db_path_main)` を無条件に呼ぶ。
バックテスト本体（`preload_data`）は Parquet しか読まないが、`init_db` が
`paths.require_existing()` / `require_populated()` の fail-fast に掛かって停止する。

```
paths.DataNotProvisionedError: システムDB (stocktool.db)が存在しません:
  ...\.claude\worktrees	lb-optimization\data\stocktool.db
```

`--mode read` は `config.local.toml` を書くだけで SQLite を用意しないため、
**バックテスト用途でも `--mode write` が要る**（`doc/agent_execution_rules.md` §10.3 の
「読み取りのみ＝`--mode read`」という対応表と実態がズレている）。

`--light` は `[light] stocktool.db は create_sandbox.py で別途構築してください` と
表示するだけで DB を作らない。`create_sandbox.py` を本体で叩くと本番の
`data/sandbox/` を触りにいく（`require_existing` が先に発火して実害は無かった）。
**`--light` を付けず実コピー（1,587MB / 十数秒）するのが確実。**

Parquet はハードリンク（実コスト 4KB）＋ポインタ書き換えなので、
本番と同一の全期間マスターを読める。

### 7-2. ベースライン trial が罰点になった — `[strategy.optimization]` の既定値書き漏らし 🔴

**現象**: 最初のスモークで trial 0（ベースライン）が **-260.96** の罰点。
検出件数 0.12件/日 で `calculate_prune_penalty` の下限割れ（`-100 - (0.2-h)*2000`）。
ドライラン実測の 2.24件/日 と3桁違う。

**原因**: `enqueue_baseline_trial()` は `[strategy.optimization]` の各キーのうち
**`strat_base` に既定値があるものだけ**を `study.enqueue_trial()` に渡す。
渡さなかったキーは **Optuna が通常どおり乱択する**。

当初 `max_vcr` と `max_sma50_atr_mult` は `[strategy.optimization]` にしか書いておらず、
`max_vcr = 0.75` が乱択された。`max_vcr` は TLB に対して最も強い絞り込みで、
0.75 は単独でも検出を 26.34 → 0.099件/日 まで落とす（下記スイープ）。
**ベースラインのつもりで測っていたものと、エンジンが評価したものが別物だった。**

**対策**: `[strategy.optimization]` の全キーに `[[strategy]]` 側の既定値を書く。
config にその旨のコメントを残した。修正後の trial 0 は **2.0件/日 / 実スコア -1.66** で正常。

> [!NOTE]
> **これは H3 固有の話ではない。** 既存戦略でも `[strategy.optimization]` にしか
> 書かれていないキーがあれば同じことが起きる。棚卸しは本タスクのスコープ外だが、
> §8 に残す。

### 7-3. 探索空間を実測で2箇所修正した

`tmp/tlb_vcr_sweep.py`（読み取り専用）。評価期間は `[optimization_periods]` の2期間、
`max_hits_per_day = 10` の枠を掛けた「エンジンの `avg_hits_per_day` と同じ土俵」で計測。

**妥当性の確認**: エンジンの trial（adr≥5.0 / rs≥0.90 / dist≥4.5 / vcr≤1.3 / satr≤5.5 / mcap≥1e9）
が **0.9475件/日** に対し、本スクリプトは **1.0062件/日**。6% 差で追随しており、
以降の数値はエンジンの挙動を予測できているとみなす。

#### (a) `max_vcr` の下限を 0.60 → 0.80 へ

| `max_vcr` | 件/日 | 判定 |
| ---: | ---: | :--- |
| 0.60 | 0.003 | prune |
| 0.70 | 0.045 | prune |
| 0.75 | 0.099 | prune |
| 0.80 | 0.184 | prune |
| 0.85 | 0.340 | 生存 |
| 1.00 | 0.951 | 生存 |
| 1.50 | 2.182 | 生存 |

他条件が既定値のとき **0.85 未満は構造的に死に領域**。0.60〜0.80 を残すと
探索の3分の1が罰点に消える。下限 0.80 だけ残して TPE に勾配を与える形にした。

#### (b) `max_sma50_atr_mult` を探索空間から削除

| `max_sma50_atr_mult` | 件/日 |
| ---: | ---: |
| 3.0 | 2.011 |
| 6.0 | 2.281 |
| 10.0 | 2.304 |

**最も厳しい 3.0 でも -13% しか動かない。** 計画段階では「H1 の 6.0〜10.0 が
死に条件なので 3.0 から探索する」としたが、実測では 3.0 でも効かなかった。
次元を1つ食うだけで情報を持たないため削除。探索は6次元 → **5次元**。

#### 探索空間の両端

- 全パラメータ最厳（adr 7.0 / rs 1.15 / dist 5.0 / vcr 0.80 / mcap 3e9）: **0.000件/日**
- 全パラメータ最緩（adr 2.0 / rs 0.90 / dist -3.0 / vcr 1.50 / mcap 1e8）: **8.005件/日**（上限 5.0 超）

両端とも罰点領域だが、これは検出件数ゲートが意図どおり効いている状態。

### 7-4. スモークの3トライアルは破棄した

### 7-5. 「境界張り付き＝最適値が範囲外」は誤読だった（§6.4 の訂正）🔴

§6.4 で3パラメータの境界張り付きを見て「探索空間が狭すぎた。範囲を広げて再探索」と結論したが、
**広げる前に実測すべきだった**。`tmp/tlb_wide_sweep.py` で best trial 163 を基準に
1パラメータずつ動かした結果、張り付きの意味は3つとも違っていた。

#### (a) `min_adr_pct_21`（上限 7.0 に 62%）— ゲートに阻まれている ✅ 実在

| `min_adr_pct_21` | 件/日 | 判定 |
| ---: | ---: | :--- |
| 7.0（現行上限） | 0.443 | 生存 |
| 7.5 | 0.333 | 生存 |
| 8.0 | 0.242 | ゲート際 |
| 8.5 | 0.176 | 罰点 |
| 10.0 | 0.071 | 罰点 |

**もっと締めたいがゲート（下限0.3 / 罰点0.2）が止めている。**
範囲を広げるだけでは罰点領域が増えるだけで、ゲート自体を開けないと評価できない。

#### (b) `min_rs_trend_s21`（下限 0.90 に 55%）— 下方向に効かないだけ ❌ 誤読

| `min_rs_trend_s21` | 件/日 |
| ---: | ---: |
| 0.925 | 0.443 |
| 0.900 | 0.451 |
| 0.850 | 0.454 |
| 0.750 | 0.454 |

**0.90 未満は1件も増えない＝母集団が同一。** 閾値フィルタなので件数が変わらなければ
選ばれる行も同一で、スコアに差が出ない。TPE から見ると勾配がゼロの平坦域なので、
**探索が下限へ漂っただけ**。範囲を広げても新しい情報は1ビットも増えない。

TLB は「カウンター線を上抜けた」銘柄なので、その時点で RS が SPY 比 0.90 を
下回っているケースがほぼ無い、というのが実態。

#### (c) `min_market_cap`（下限 1e8 に 100%）— 同じく効かないだけ ❌ 誤読

| `min_market_cap` | 件/日 |
| ---: | ---: |
| 1e8 | 0.443 |
| 5e7 | 0.448 |
| 1e7 | 0.449 |
| 制約なし | 0.451 |

母集団の内訳を見ると理由がはっきりする（best trial 163 の条件下・全期間）:

| 時価総額 | 件数 | ADV 中央値 |
| :--- | ---: | ---: |
| 〜$10M | 1 | $4.1M |
| $10M〜$50M | 1 | $2.1M |
| $50M〜$100M | 4 | $3.0M |
| $100M〜$1B | 158 | $6.3M |
| $1B〜 | 199 | $41.7M |

**$100M 未満は全期間で6件しか無い。** `[general]` の流動性床 $2M が先に効いていて、
時価総額の下限はほぼ無意味になっている。ユーザーの「件数の微調整に使える」という
経験則は他戦略では成り立つが、**TLB では流動性床と重複していて効かない**。

#### 教訓

**境界張り付きを見たら、範囲を広げる前に「その方向に効くのか」を実測する。**
効かない方向への張り付きは「最適値が外にある」ではなく「勾配がゼロ」のサイン。
今回は広げる前に測ったので、無駄な200トライアルを1本節約できた。

### 7-6. H3b — ゲートを開けた再探索（実行中）

§7-5 (a) を受けて、H3 との設計差を**検出件数ゲートの2行だけ**にした
`H3b_structure_tlb_tight` を追加した。

```toml
min_avg_hits_per_day = 0.05   # E1（VCP ブレイクアウト）と同じ
min_hit_rate_pct = 0.3        # 同上
```

`resolve_prune_floor()` と `quality_gate` はどちらも「戦略側がより低い値を宣言していれば
それを尊重する」流儀なので、この1行で罰点下限もゲート下限も 0.05 に下がる。
あわせて `min_adr_pct_21` の上限を 10.0、`max_vcr` の下限を 0.70 に戻した
（H3 では罰点だった領域が評価可能になるため）。

`min_rs_trend_s21` と `min_market_cap` は §7-5 (b)(c) より**広げない**。

ベースライン（trial 0）は H3 の best trial 163 の値を置いた。

> **この study の目的は最良パラメータ探しではなく「締めるほど質が上がり続けるか」の確認。**
> 検出が薄くなるぶん統計は粗くなるが、`expectancy_lcb` は標本数を織り込む
> （期待値 − 2×SE）ため、薄さゆえの見かけの良さは自動的に割り引かれる。
