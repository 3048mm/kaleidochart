## 1. 背景と目的

### きっかけ

2026-08-05、改称6件を適用して `--rebuild-from T4` を**5時間**実行したが、
Parquet の T4 は **730日窓の500行しか埋まらなかった**。

```
FOCL/HAPN/SHOE/NSLR  T3=2096  T4=500
AAPL（対照）          T3=2096  T4=2096
```

**原因**: T4 は **SQLite の `indicators` に存在する日付しか計算できない**。
SQLite は730日分しか持たないため、全期間を埋めるには
`run_production_restore.py`（SQLite を全期間復元）→ `--rebuild-from T4` の
2段階が必要で、**約3.5時間**かかる。

### なぜ部品化するか

同じ「Parquet 上で過去を再計算する」能力が、独立に3箇所で必要になる。

```
parquet_recompute（本計画）
  ├─ 改称・新規銘柄追加後の T4 補完          ← 今すぐ必要
  ├─ 分割・併合の価格補正（split_anomaly 計画） ← 補正を実装する段階で必須
  └─ restore_truncated_symbol_history        ← 既存の「T4 は別途」を解消
```

`restore_truncated_symbol_history.py` は T3 までは Parquet 上で再計算していたが、
**T4 だけ「後で `--rebuild-from T4` を回せ」と外部に投げていた**。そこが今回の穴。

### ベースライン（2026-08-05 実測）

| 経路 | 所要 | SQLite への影響 |
| :--- | ---: | :--- |
| 現行（restore → `--rebuild-from T4`） | **約3.5時間** | DB 削除・再構築を伴う |
| **Parquet 直接再計算** | **約4分** | **接続ゼロ** |

`PERCENT_RANK()` の pandas 再現は**実データで完全一致**を確認済み
（2026-07-31 の3,190行、最大誤差 0.000e+00）。

## 2. スコープと設計判断

### 2.1 変更すること

1. **`backend/pipeline/parquet_recompute.py`**（新規）— 再計算の共通部品
   - `recompute_ranks()` … T4 を日付×カテゴリで再計算（全期間4分）
   - `recompute_indicators()` … T3 を銘柄単位で再計算（既存実装を移設）
   - `find_affected_virtual_themes()` … 補正銘柄 → 所属仮想テーマの逆引き
2. **今回の T4 欠落6銘柄を解消**（本番 Parquet に適用）
3. `restore_truncated_symbol_history.py` を本部品へ寄せる

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 | 理由 |
| :--- | :--- | :--- |
| `PERCENT_RANK` の実装 | **`(rank(method='min') - 1) / (n - 1)`、NULL は `-inf` 扱い** | SQLite は NULL を最小値とする。`rank(pct=True)` では**一致しない**（`rank/n` になる）。実データで完全一致を確認済み |
| 歴史的な `active` の再現 | **しない。現在の `active` を使う** | 過去の active 状態を記録していない。SQLite の T4 も現在の `active` で計算しており、**既存の慣習に合わせる** |
| 仮想テーマ価格の再合成 | **本計画では実装しない**（§8） | 今回の T4 欠落には不要。分割補正を実装する段階で追加する。ただし**逆引き関数だけは先に用意**する |
| SQLite 側の T4 | **触らない** | 730日窓は日次パイプラインが正しく維持している。Parquet だけを直す |

### 2.3 判明した重要な副作用

**非 active 銘柄が Parquet に古い順位を持ち続けている。**

```
非 active 15銘柄が持つ ranks: 26,649行（2018-04-02〜2026-07-31）
```

Parquet の時系列テーブルは**マージのみで行削除がない**ため、退役・改称で `active=0` に
なった後も過去の行が残る。SQLite 側は再計算時に除外するが、その「不在」は伝播しない。

**再計算すると、この26,649行は母集団から外れる。** 影響:

- **バックテスト結果への直接影響はない**（`backtest_screener.py:160` が `active == 1` で
  除外するため、順位行があってもなくても候補にならない）
- **他銘柄のパーセンタイル値は変わる**。母集団が 15件減り 6件増えるため、
  約2,900銘柄に対し 0.7% 程度の population 変化
- したがって**過去の最適化結果は厳密には再現しなくなる**

## 3. 変更内容

### 3.1 `recompute_ranks()`

`t4_ranks.py` の SQL と等価な計算を pandas で行う。

```
PERCENT_RANK() OVER(PARTITION BY s.category ORDER BY i.{col} ASC)
  ↓
df.groupby(['date','category'])[col].transform(percent_rank)
```

- 対象カテゴリ: `レバレッジ` / `指標` を除く（`t4_ranks.py` の `NOT IN` と同じ）
- 対象銘柄: `active == 1`
- 対象日: `min_allowed_date`（既定 2018-04-01）以降
- 22の指標列 → 22のランク列（マッピングは `t4_ranks.indicators_to_rank` と同一に保つ）

### 3.2 検証（実装の正しさをどう担保するか）

**既存の Parquet と突合する。** 直近730日は 2026-08-05 の `--rebuild-from T4` で
SQLite 経由で正しく計算されているため、**再計算結果がそれと一致すれば実装は正しい**。

```
再計算 vs 既存（2024-08-05 以降・active 銘柄のみ）→ 一致すべき
再計算 vs 既存（2024-08-04 以前）              → 6銘柄が増え、15銘柄が消え、他は微変動
```

### 3.3 適用

MVCC で新世代を書き、pointer を更新する。**旧世代は prune しない。**

## 7. 途中発生した課題

### 旧 Parquet に NULL のランクを 1.0 としている行が 1,348 行あった

再計算との差分検証中に「最大変動 1.000e+00」が出た。母集団の変化では説明できない大きさ
だったため調査したところ、**2024-08 以前の仮想テーマ（`_FNTC39_` `_GRCL0C_` 等）で
NULL 値のランクが 1.0（最大）になっていた**。

SQLite の実挙動を直接確認して決着させた:

```
合成テスト  VALUES (NULL),(10),(20),(30) → NULL の percent_rank = 0.0
本番データ  AIPO の rs_ratio_e5=NULL → ランク 0.0
```

**旧コードの誤りであり、本実装での再計算により修正された**（1,348行 / 全体の0.023%）。
実装側のバグではなかった。

### 検証テストの方が誤っていた（一度、実装を疑った）

既存 Parquet の ranks 行をそのまま母集団として突合したところ系統的に `1/(n-1)` ずれた。
原因は **既存 ranks に退役済み銘柄の残骸が1行混入**していて n が1件多かったこと。
SQLite を正として突合し直したところ完全一致した。
**「既存データ」を正解として扱う前に、それ自体が汚染されていないか確認すること。**

## 8. スコープ外・残作業

- **仮想テーマ価格の再合成**は本計画では実装しない。
  仮想テーマは構成銘柄のリターンを連鎖させて算出しており、
  再計算モードは**構成銘柄の集合のハッシュ**（`data/virtual_theme_hashes.json`）で決まる。
  **構成銘柄の「価格」が変わってもハッシュは変わらない**ため、
  差分モードのまま過去が再計算されない。
  実測: 仮想テーマ170件・構成ペア1,462件（平均8.6銘柄/テーマ）、
  1銘柄が最大5テーマに所属（`RKLB` `NET` `HPE` `CIEN` `CGNX`）。
  分割補正を実装する段階で、強制 rebuild の手段とあわせて追加する。
- T5（market_signals）の再計算も本計画では扱わない。
