## 1. 背景と目的

### 発見の経緯

P1「分割・統合の検証手段」で `SOXS`（3倍インバース半導体ETF）の2026-05-26の価格段差を
moomoo APIで確定し、本番データを補正した（`doc/completed/moomoo_split_verification_plan.md`）。
補正後に `db_health_check.py --check-nulls` を回したところ、`rs_ratio_e21`/`rs_momentum_e21`の
NULL件数が全期間で **1,387件 → 987件に改善**した一方、**直近4日（2026-09-04〜09-10）に
新規4件が発生**した。これを調査した結果、**補正そのものが原因ではなく、元々`relative_strength.py`
に存在した数値精度の不具合が、価格の書き換えにより発生箇所がずれただけ**と判明した。

### 根本原因（再現・特定済み）

`relative_strength.py` の `rs_ratio_e{n}` は次のように計算される（`n`=5/14/21/63/200）:

```python
rs_ema = calculate_ema_tv(rs, n)                          # 全履歴に対する再帰EMA
rs_mean = rs_ema.rolling(window=n, min_periods=max(1, n//2)).mean()
rs_std  = rs_ema.rolling(window=n, min_periods=max(1, n//2)).std()
df[f'rs_ratio_e{n}'] = np.where(
    rs_std.isna() | (rs_std == 0), np.nan, (rs_ema - rs_mean) / rs_std
)
```

`rs_momentum_e{n}` も同型（`roc_ema.rolling(window=n).std()`）。

**`SOXS`は過去9回の併合（2013〜2026年、倍率4/4/5/10/12/10/10/20/10）を経ており、
累積調整の結果2010年代の`close`が数十億〜数千億ドル相当という桁外れの値になっている**
（例: 2010-04-01 の `close` は 4.19×10^11）。これ自体は補正とは無関係な既存の特性で、
`SOXS`がT4横断ランク・バックテスト母集団から除外済み（`category='レバレッジ'`）のため
実害はない。

問題は、`.rolling(window=n).std()` が**全履歴に対して1回の呼び出しで計算**されること。
pandasの`.rolling().std()`は**逐次更新（インクリメンタル）方式**で分散を計算するため、
履歴の初期（2010年代、数十億〜数千億ドル相当）を通過する際に生じる浮動小数点誤差が、
**何年も後の、桁が全く違う（0.06前後の）区間の計算まで汚染**し、`rs_std`が厳密に
`0.0`になる（結果、`rs_ratio_e21`がNULLになる）。

### ベースライン（着手前の実測）

2026-09-12、本番データ（`data/parquet_master/`、`SOXS`の価格補正後）で実測:

```python
# 2026-08-15〜09-11の21日窓のrs_ema（実際の値、19個ユニーク・正常に変動している）
vals = [0.060268081831616652, 0.060023737636513662, ..., 0.061442298537268805]

# pandas .rolling(21).std()（全履歴からの逐次計算）
rs_std == 0.0   # ← これが原因でrs_ratio_e21がNaNになる

# 同じ値をnumpyで独立に計算した場合
np.std(vals, ddof=1) == 0.0009597459434902306   # ← 正常な非ゼロ値
```

本番の`SQQQ`・`BOIL`（他の高倍率レバレッジ/インバースETF）も**同型の恒常的な1件NULL**を
`db_health_check.py`で確認済み（`SOXS`補正前から存在）。累積併合で価格レンジが極端に
広い銘柄全般に潜む問題と考えられるが、**網羅的な棚卸しはまだ行っていない**（§5参照）。

### 目的

この問題を解消し、極端な価格レンジを持つ銘柄でも `rs_ratio_eN`/`rs_momentum_eN` が
正しく計算されるようにする。あるいは、正しく計算できない銘柄を明示的に切り分けて
NULL以外の扱い（警告付きスキップ等）にする。

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 |
| :--- | :--- |
| `SOXS`等の価格スケール自体（2010年代が数十億ドル相当になる特性）を修正する | **しない**。これは分割・併合の累積調整として数学的に正しい結果であり、`upstream-data-diagnosis`の限界カタログにも「補正不要」と整理済みの特性（`doc/completed/moomoo_split_verification_plan.md`参照）。直す対象は「その値でも指標計算が壊れないこと」であって「値自体を常識的な範囲に収める」ことではない |

## 3. 変更内容（対応案。§4でユーザーが1つを選ぶ）

1. **`rolling(window=n).std()`の計算範囲を全履歴ではなく直近の妥当な範囲に絞る**
   （例: 銘柄ごとに直近5年分だけを対象にrollingを計算し直す、または計算前に系列を
   チャンク分割する）。実装コストは中程度。既存の値が変わりうる範囲を要検証。
2. **pandasの`.rolling().std()`をやめ、数値的に安定な独立計算に置き換える**
   （例: `.rolling(n).apply(lambda x: np.std(x, ddof=1), raw=True)`）。
   ロジックの変更は最小だが、**計算コストが増える可能性がある**
   （全銘柄・全期間・複数nでの実行時間への影響を計測すること）。
3. **価格レンジが極端な銘柄を検出し、RS計算の対象から除外するか警告を出す**
   （例: 累積分割・併合倍率が閾値を超える銘柄をフラグ立てする）。
   実装コストは低いが、**対症療法**であり根本原因は残る。

## 4. ユーザー確認事項（2026-09-12 合意済み）

1. **対応案: 案2「numpyでの独立計算」を全銘柄に適用する（確定）。**
   棚卸し結果（§5作業中メモ）を提示した上でユーザーが選択。しきい値検出による
   ハイブリッド適用（対象を価格レンジ極端な銘柄に絞る案）も提示したが、
   「価格レンジは決定的な判別式ではない（`ORLA`等の反例あり）」という棚卸し結果を
   踏まえ、**全銘柄に一律適用**を選んだ。実装は`rolling(window=n).std()`を

2. **棚卸しの順序: 対応案を決める前に実施済み（2026-09-12）。** 結果は§5「作業中メモ」。
3. **性能への影響: 実装後に実測し、許容できない増加があれば都度報告する。**

### 作業中メモ

#### 2026-09-12 棚卸し結果（`tmp/rs_std_precision_inventory_v2.py`、読み取り専用・本番Parquet3世代 `20260912_145123` を対象）

**手法**: `indicators`（全銘柄・全履歴、676万行）から `rs_value` の有効日数カウンタを作り、
各 `rs_ratio_e{n}`（n=5/14/21/63）について「有効日数が `3n` 以上（=ウォームアップを
確実に抜けた成熟区間）なのにNULL」を異常候補として抽出。`rs_value.rolling(n,
min_periods=n//2)` の後段でさらに `rs_ema`（EMA平滑化後の系列）に対する
`rolling(n).std()` を取るため、ウォームアップは `n` ではなく実質 `1.5〜2n` 程度
まで尾を引く（初回 `閾値=n` で試したところ中央値が `min_periods-1` と完全一致し、
ウォームアップ由来と判明・棄却。`3n` に引き上げて再実行）。

**結果: `rs_ratio_eN`（根本原因が直撃する層）で異常が出たのは全3,279銘柄中わずか6銘柄**:

| ticker | category | log10(価格レンジ) | 価格レンジ倍率 | 異常件数(e5/e14/e21/e63/e200) |
| :--- | :--- | ---: | ---: | :--- |
| SOXS | レバレッジ | 8.92 | 約8億倍 | 1298/0/872/789/0 |
| SQQQ | レバレッジ | 5.40 | 約25万倍 | 329/263/199/20/0 |
| BOIL | レバレッジ | 5.62 | 約42万倍 | 115/102/36/0/0 |
| NVVE | 個別株 | 6.85 | 約700万倍 | 0/41/13/0/0 |
| FAZ | レバレッジ | 4.22 | 約1.6万倍 | 27/0/0/0/0 |
| MNTS | 個別株 | 5.03 | 約10万倍 | 2/0/0/0/0 |

- **`rs_ratio_e200`（最長窓）は6銘柄すべてで異常0件** — 窓が長いほど数値的に頑健、という
  仮説と整合。
- **個別株（`NVVE`/`MNTS`）にも波及していた** — レバレッジETF固有の問題ではなく、
  「価格レンジが極端に広い（分割・併合の累積調整、または実際の株価変動）」という
  共通性質が真因であることを裏付ける（§2.2の想定どおり）。
- **ただし価格レンジ倍率は完全な判別式ではない**: `ORLA`(10^5.34倍)・`UAVS`(10^4.46倍)・
  `LABD`(10^4.43倍、レバレッジETF)・`FLZH`(10^4.39倍)・`STKH`(10^4.02倍)は
  今回の閾値では異常0件だった。異常が出た6銘柄はいずれも log10レンジ≧4.2だが、
  同程度以上のレンジを持つ銘柄でも発生しない例がある＝価格レンジは強い相関因子だが
  「レンジがXを超えたら必ず発生する」という単純な決定的しきい値ではない
  （pandasの逐次std計算がどの区間でキャンセレーションを起こすかは、レンジの大きさに
  加えて値の変化パターンにも依存すると考えられる）。

**`rs_momentum_eN` は別の切り分けが必要**: 同じ`3n`閾値では3,000銘柄超（ほぼ全銘柄）で
中央値10〜16件の"異常"が出たが、`rs_momentum_eN`は`rs_ratio_eN`→`ROC`→`EMA`→
`rolling.std()`と計算段が1つ多く、ウォームアップも長引く（`3n`では不足）。この層は
今回切り分けきれておらず、**§3の対応方針を決める材料としては`rs_ratio_eN`の6銘柄を
主として扱う**（`rs_momentum_eN`側は同じ根本原因が上流の`rs_ratio_eN`から伝播している
可能性が高く、`rs_ratio_eN`を直せば連動して改善すると推測されるが未検証）。

**結論**: 「他の銘柄への波及」は**あるが限定的**（3,279銘柄中6銘柄=0.18%）。
価格レンジとの相関は明確（Pearson 0.30〜0.35, 全異常銘柄がlog10レンジ≧4.2）だが、
完全な決定的しきい値ではないため、**§3対応案3（しきい値検出による除外/警告）単独では
将来の未知銘柄を見逃すリスクが残る**。案2（numpyでの独立計算）は「異常候補6銘柄のみ」に
適用すればコスト増を全銘柄の0.18%に限定できるため、コスト面の懸念（§4-3）は
大幅に緩和される可能性がある（性能実測はこれから）。

## 6. 検証プラン / 結果

### 検証方法

- 極端な価格レンジを持つ合成データ（例: 前半1000日を1e10スケール、後半を1.0スケールに
  した合成系列）で、修正前は`rs_std==0.0`になり修正後は正常な非ゼロ値になることをテストで固定する
- `SOXS`/`SQQQ`/`BOIL`の実データで、修正後に該当NULLが解消することを確認する
- 通常銘柄（例: `AAPL`）で修正前後の`rs_ratio_e21`等の値が完全一致することを確認する
  （既存の計算方法を壊していないことの保証）

### 6.0 実装・検証結果（2026-09-12、ワークツリー`rs-std-precision`）

**実装**: `backend/indicators/relative_strength.py` に `rolling_std_independent()` を追加
（numba `@njit` カーネル、2パス法: 平均→偏差二乗和でddof=1のstdを毎ウィンドウ独立に計算）。
`rs_std`/`roc_std`（計2箇所×n=5/14/21/63/200）を `.rolling().std()` からこれに置き換え。
`rs_mean`/`roc_mean`は変更していない（pandasの`.rolling().mean()`のまま。§3の対応案2の
記述どおりstdのみが対象）。

**合成データでの再現・修正確認**: 前半1200日を1e10スケール、後半1200日を100前後スケール
にした合成系列で、修正前は成熟区間（後半に入って100営業日以降）で`rs_ratio_e14`が
1081/1100件（98%）NULL、`rs_ratio_e63`が645/1100件（59%）NULLになることを確認
（`rs_ratio_e21`はNULLにはならなかったが、値が独立numpy計算比で**650倍**ずれていた:
0.47 vs 0.0007 — NULLだけでなく**値そのものが壊れるケース**も存在することが判明）。
修正後は全n・全区間で異常NULL 0件、`rs_ratio_e21`の値も独立numpy計算と小数点5桁まで一致。

**本番相当データでの検証**（sandbox、hardlinkされた本番Parquet世代`20260912_145123`）:
棚卸しで判明した既知6銘柄（`SOXS`/`SQQQ`/`BOIL`/`NVVE`/`FAZ`/`MNTS`）と対照銘柄`AAPL`に
ついて`calc_relative_strength`を直接実行。**修正後は7銘柄すべてが同一の
「warmupのみに由来するNULLパターン」**（各n値のNULL件数が銘柄間で完全一致: e5=5, e14=19,
e21=29, e63=92, e200=298）に揃った。これは、価格レンジに関わらずEMA+rolling.std()の
構造上必要なウォームアップ日数だけがNULLの原因として残り、価格レンジ由来の異常NULLが
完全に解消したことを意味する。

**性能measurement**:
- `calc_relative_strength`全体（サンプル300銘柄、active）: 平均約30ms/銘柄
  （初回のnumba JITコンパイル約1.1秒を除く）。全3,279銘柄換算で**約106秒**。
- std計算部分のみのマイクロベンチマーク（1銘柄相当=n×2箇所×5系統=10回呼び出し）:
  旧実装(pandas) 8.02ms/銘柄 → 新実装(numba独立計算) 29.24ms/銘柄。
  **全銘柄換算の増分は約+70秒**（26.3秒→95.9秒）。

### 6.1 反証 — この結論が誤りだとしたら、何が観測されるはずか

- **この結論（pandasの`.rolling().std()`の逐次計算精度が原因）が誤りだとしたら**:
  同じ21日分の値を独立にnumpyで計算した場合も`0.0`に近い値になるはず。
  実際には`0.00096`という明確な非ゼロ値が得られており、**独立経路（numpyでの計算）で
  確認済み**。この反証は着手前（2026-09-12の発見時点）に実施済み。
- **§2.2で保留した「他の銘柄への波及」の反証**: この結論が誤りで実は影響がSOXS等の
  極少数銘柄に留まらないとしたら、棚卸し（§5）で価格レンジが極端ではない銘柄にも
  同型のNULLパターンが見つかるはず。**棚卸し実施済み（2026-09-12）**:
  価格レンジが極端でない銘柄（log10レンジ<4.2）では`rs_ratio_eN`の異常NULLは
  1件も見つからず、反証は成立しなかった（＝当初の結論を補強）。ただし価格レンジが
  極端な銘柄の中にも異常が出ないケースがある（`ORLA`等）ため、「価格レンジのみで
  完全に予測できる」という強い主張はできない。詳細は§5「作業中メモ」参照。
