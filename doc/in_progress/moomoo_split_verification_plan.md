## 1. 背景と目的

`scan_split_consistency.py`（第1・2段階）は「上流(yfinance)自身の自己矛盾」と「手元/上流のスケール乖離」を
検出できるようになり、2026-09-10 に本物のデータ破損2件（`IESC`/`WLFC`）を検出・補正済み。

しかし**上流が分割記録そのものを持たない銘柄は原理的に検出できない**。現状の未決着候補:

| 銘柄 | 状態 | 詳細 |
| :--- | :--- | :--- |
| `SOXS` | 監視のみで確定（2026-08-06） | 観測比 0.054 から 1:20 を推定しているが上流に記録が無く未確認。レバレッジETFでT4対象外のため実害は無いが、確定はできていない |
| `STKH` ほか7件 | 「近傍だが比が一致しない」報告のみ（2026-09-10） | `STKH` は分割 2026-07-27 ×1:3（期待比3.0）に対し実測段差2.6667＝11%外れ。分割が中途半端に効いた可能性と、分割日に別途11%下げた可能性の両方が読める |

本計画の目的は、**上記のような少数の未決着候補について、yfinance以外の独立ソース（moomoo）で
分割記録を取得し、判定材料を追加すること**。自動修正はしない（第1・2段階と同じ方針）。

### ベースライン

- 現時点の「要対応・要確認」候補: 1件（`SOXS`、監視のみで確定済みだが根拠が推定）+ 近傍不一致8件（うち際どいのは`STKH`1件）
- 候補は今後 `scan_price_anomalies.py` が `split_suspect`（`split_match` 無し＝比・出来高ヒューリスティックのみで判定）
  を新たに出すたびに増える。件数は2026-09-10時点で1,357件中1件のみ（`split_suspect` は0件、`market_wide`/`real_move`
  に紛れているものが本当の対象）

## 2. スコープと設計判断

### 2.1 変更すること

- moomoo APIから個別銘柄の分割・配当記録（`get_rehab`／REST `rehab` エンドポイント相当）を取得する薄いクライアントモジュール
- 候補ティッカーを明示指定して実行する手動CLIスクリプト。`data_collection/split_records.py`（yfinance側の記録）
  および `scan_price_anomalies.py` の分類結果と突き合わせ、一致/不一致/moomoo側にも記録なし、を報告する
- `.claude/skills/upstream-data-diagnosis/SKILL.md` §6 に手順・実績を追記
- `doc/issue_list.md` P1 該当項目の更新

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 |
| :--- | :--- |
| 全銘柄をmoomooでバッチ照合する | **しない**。候補は現状10件未満。moomoo側の認証が手動性を伴う（後述）ため、`scan_split_consistency.py` 自身がまだ週次に組み込まれていない（単体運用で精度検証中）のと同じ段階に置く。週次自動化は別issueで判断する |
| moomoo側の判定で自動修正する | **しない**。moomooも「もう一つの独立ソース」に過ぎない。2026-09-04のMNST事故（上流一致を歯止めにした結果、壊れた上流に合わせて正しいデータを壊した）の教訓から、**判定は引き続き人間に残す**。スクリプトは報告のみ |
| moomooを本番パイプラインの分割メタデータ源として常用する | **しない**。あくまでyfinanceの記録が欠落・曖昧な少数ケースの決着用。定常運用のデータ取得経路は変えない |
| ポートフォリオ機能のmoomoo証券API連携（`doc/issue_list.md` P3）と統合する | **しない**。あちらは保有銘柄の自動同期が目的で用途が別。本計画は分割記録の参照のみに使う独立した薄いクライアント |

## 3. 変更内容

- `backend/data_collection/moomoo_client.py`（新規）: 認証済みセッションから分割・配当記録を取得する薄いラッパー。
  ネットワーク呼び出しは関数境界で切り出し、テストはモック応答で行う（実アカウントが無くてもユニットテストは通る）
- `backend/scripts/verify_split_with_moomoo.py`（新規）: `--tickers` 必須（全銘柄スキャンは提供しない）。
  moomoo側の分割記録 vs `data/maintenance_reports/split_records.json`（yfinance側）を突き合わせて報告する。
  CBOE連携（`backfill_vix_from_cboe.py`）の「重複検算してから採用する」原則を踏襲し、
  既知の正しく適用された分割（例: 直近の大型株の分割）で応答形状・値を検算する自己診断コマンドを用意する
- 認証情報（APIキー/トークン）は `config.local.toml` 等の git 管理外ファイルに置く（`tools/provision_worktree_data.py`
  が生成する `prod_root` 設定と同じ扱い）

## 4. ユーザー確認事項

1. **moomooアカウント登録はユーザー自身が行う必要がある。** SMS認証・利用規約同意を含むアカウント作成は
   Claude Codeが代理実行できない。着手前にユーザー側でのアカウント作成をお願いしたい（口座開設・入金は不要と確認済み）。

2. **アクセス方式の選択（要判断）**:

   | 方式 | 特徴 |
   | :--- | :--- |
   | A. OpenD gateway + Python SDK（`pip install moomoo-api`） | `openapi.moomoo.com` 配下でドキュメントが厚い。米国LV3市場データ（Nasdaq Basic+TotalView, NYSE ArcaBook）が**現在プロモーションで無料**と確認済み。`get_rehab`（分割日・分割比・配当・前方/後方調整係数）のフィールド仕様も確認済み。ただし**OpenD常駐プロセス＋初回SMS認証**が要り、長時間の無人稼働にはトークン失効の考慮が要る |
   | B. Gateway-free REST API（`open.moomoo.com`） | OAuth 2.1+PKCE または APIキー。ゲートウェイ常駐が不要で自動化しやすい。`/api/quote/basic-data/rehab` エンドポイントの存在は確認したが、**米国市場データの権限・料金体系はドキュメントから確認できなかった** |

   **推奨: まずA。** 実績のあるドキュメントで無料枠を確認済みであり、本計画は手動実行前提（§2.2）なので
   OpenD常駐の運用負荷は問題にならない。将来自動化する段になったらBへの移行を検討する。

3. **初期対象候補**: `SOXS`（監視のみで確定済みだが根拠未確認）と、近傍不一致8件（`STKH`ほか、
   `doc/completed/split_aware_anomaly_classification_plan.md` §7 参照）。将来 `scan_price_anomalies.py` が
   新たに `split_suspect`（`split_match`無し）を出した銘柄も同スクリプトで照合できるようにするが、
   **全銘柄バッチ化はしない**（§2.2）。

4. **「プロモーションで無料」が今後有料化された場合の扱い**: 発生時点で都度判断する。
   無料枠が終わったら本検証手段自体の費用対効果を再評価し、issue化する。

5. **既知の未確定点**: 米国株（Nasdaq/NYSE個別銘柄）の `get_rehab` が実際に正しい分割記録を返すかは、
   公開ドキュメントの記述（`Security` 構造で複数市場に対応、対象市場の明記なし）からの推測であり、
   **実際にアカウントを作って `SOXS` 等で試すまで確定しない**。これはチェックリストの最初の実データ確認項目として扱う。

### 6.1 反証 — この結論が誤りだとしたら、何が観測されるはずか

- **この結論（moomooが有効な独立ソースになる）が誤りだとしたら観測されるはず**:
  実際に `get_rehab` を叩いた際、米国株（Nasdaq/NYSE個別銘柄）で空/エラーが返る、無料枠に米国個別株の
  ヒストリカル分割記録が含まれない、または返る値がyfinance/TradingViewの実測と食い違う、のいずれか
- **独立経路での確認**: 未実施（moomooアカウントが未作成のため）。着手時の最初の実データ確認チェックリスト
  項目（自己診断コマンド）でこれを潰す。既知の正しく適用された分割で値が一致することを確認してから、
  `SOXS`/`STKH` の判定に使う
