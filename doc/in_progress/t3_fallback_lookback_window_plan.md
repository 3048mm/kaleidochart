## 1. 背景と目的

2026-09-26 の日次更新で、T3 の `null_recursive_column`（増分計算の状態が壊れていると判定された銘柄）が急増した。

| 日時 | 増分不可→全期間計算 | うち欠陥判定 | ウォームアップ中 | 判別不能 |
| :-- | --: | --: | --: | --: |
| 2026-09-24 08:10（昇格前） | 366 | 0 | 100 | 41 |
| 2026-09-25 07:55（昇格後1回目） | 395 | 0 | 92 | 73 |
| 2026-09-25 13:55 | 396 | 4 | 91 | 75 |
| **2026-09-26 08:02** | 390 | **93** | **0** | 74 |

本番 SQLite で判定を再現した結果（`tmp/` ではなくスクラッチで実施。§6 に手順）: **欠陥 95 銘柄はすべて `rs_roc_ema_200` の1列のみ**、うち 91 銘柄は **2026-09-24 の行から NULL に戻った**（SETM・IBIT・ARM・ABVX など上場から約 611〜1,011 本の銘柄）。

### 1.1 発生の仕組み

1. `rs_roc_ema_200` の必要本数（`warmup_bars`）は A-full 後 **611 本**。SQLite の保持は約 **504 本**、増分ウィンドウ K は **400 本**
2. 昇格時の T3 全期間再計算は **Parquet 基点**なので、履歴が 611 本を超える銘柄には正しい値が入った
3. 翌日の日次更新: 増分ウィンドウ（400本）の中で `rs_roc_ema_200` が **NULL→値あり**に切り替わっている銘柄は、現行判定（`t3_indicators.py:182-224`）が「ウィンドウ内に1つでも NULL があれば増分不可」とするため `warmup_in_progress` として**全期間計算へフォールバック**
4. そのフォールバックは **SQLite の 504 本だけ**で計算するため 611 本に届かず、**新しい行に NULL を書く**
5. 翌日、「値→NULL に戻った」＝単調性の破れとして `null_recursive_column`（欠陥）判定

既存 issue「`rs_roc_ema_200` が NULL の40銘柄」は、昇格前（warmup 511 vs 保持 504）に同じ仕組みで少数だけ出ていたものと推定する。A-full で 611 に伸び、昇格で全銘柄がいったん正しい値に揃ったことで一斉に表面化した。

### 1.2 放置した場合

対象銘柄は毎日フォールバックし続け、`rs_roc_ema_200`・それに依存する `rs_momentum_e200`（810本）・関連ランク（T4）に NULL を書き続ける。上場から約 1,011 本（611 + K）を超えるまで解消しない。

### 1.3 完了時の状態（成功条件）

1. NULL→値ありへ単調に移行済みで、前日行に値がある RECURSIVE 列は、**増分計算で正しく継続**される（全期間計算＝Parquet 基点の値と一致）
2. 既存の NULL（約95銘柄）が `--rebuild-from T3` で修復され、**翌日以降の日次更新で再発しない**（`null_recursive_column` が 0〜数件に戻る）
3. §1.4 の残るケース（C）は issue として起票されている

### 1.4 この計画で直らないケース（重要）

**前日行が NULL のまま、真の履歴で 611 本目を越える銘柄**（今日の「判別不能 74 件」がその手前にいる）。シードが無いので増分計算できず全期間計算に回るが、SQLite 504 本では 611 本に届かず、**NULL が永続化する**。直すには全期間計算を Parquet 基点にする（案 C）しかない。発生ペースは「判別不能 74 件が約 200 本の区間に分布」から **およそ週 2 銘柄**と見積もる（実測ではない）。

## 2. スコープと設計判断

### 2.1 変更すること

1. **フォールバック判定（`t3_indicators.py:182-224`）を絞る（案 B）** — RECURSIVE 列について、ウィンドウ内に NULL があっても「**単調（値→NULL の戻りが無い）かつ最終供給行（前日）に値がある**」なら増分計算を続ける。フォールバックは「単調性の破れ（欠陥）」「前日行が NULL（シード無し）」の場合だけにする
2. **merge 後、`--rebuild-from T3` で既存の NULL を修復する（案 A）** — `deploy_after_merge.ps1`（既定 `--rebuild-from T3`・Parquet 基点）を使う
3. **ログの分類名を実態に合わせる** — `warmup_in_progress` は「増分継続」になるためフォールバック理由から消える。ログ文言・docstring を更新

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 |
| :-- | :-- |
| 案 C（フォールバックの全期間計算を Parquet 基点にする） | **本計画では行わない（別 issue）。** §1.4 のケースの根治策で R19（週次メンテの自己修復）と同じ直し方になるが、毎日約 390 銘柄ぶんの Parquet 読み込みコスト・変更規模が大きい。B で 95 銘柄の再発を止めることを先にする（2026-09-26 ユーザー判断: B→A） |
| 増分ウィンドウ K（400）を広げる | **行わない。** SQLite の保持 504 本が上限で、611 本には構造的に届かない |
| `warmup_bars` の値の変更 | **行わない。** 611 は Parquet 全履歴での実測値で正しい |
| 欠陥判定（単調性の破れ）の条件 | **変えない。** 値→NULL の戻りは引き続き欠陥としてフォールバック・警告する |

## 3. 変更内容

### 3.1 判定の是正（`backend/pipeline/phases/t3_indicators.py`）

現行: `rec_cols` の各列について「ウィンドウ K 本すべて非 NULL」でなければフォールバック。

変更後の分類（列ごと）:

| ウィンドウ内の状態 | 現行 | 変更後 |
| :-- | :-- | :-- |
| 全行非 NULL | 増分 | 増分（変更なし） |
| NULL→値ありへ単調・**最終行に値あり** | `warmup_in_progress` でフォールバック | **増分を継続** |
| 値あり→NULL に戻る（単調性の破れ） | 欠陥でフォールバック | 欠陥でフォールバック（変更なし） |
| 全行 NULL・`warmup_bars < K` | 欠陥 | 欠陥（変更なし） |
| 全行 NULL・`warmup_bars >= K` | 判別不能でフォールバック | 判別不能でフォールバック（変更なし。§1.4） |

**増分計算が正しい根拠**（`incremental_merge.py` の契約）: RECURSIVE 列は前日行（K−1 行目）の値をシードに最終行だけを1歩計算する。WINDOW 列（`rs_momentum_e200` 等）は供給済みの RECURSIVE 列に対して通常の rolling（`min_periods=window`）をかける。ウィンドウ前半の NULL が真のウォームアップと一致している（単調）限り、rolling が NaN を返す範囲も真の値と一致する。**この前提はテストで実証する（5-2）**。

### 3.2 影響範囲

- 対象は RECURSIVE 21 列すべてに効くが、実際に「ウィンドウ内に遷移がある」状態が長く続くのは warmup が大きい `rs_roc_ema_200`（611）程度。他の列は warmup が K より十分小さく、遷移はすぐウィンドウの外へ出る
- データ形状は変わらない。値が変わるのは「本来 Parquet 基点で値が入るべき行」だけ（NULL→正しい値）

## 7. 途中発生した課題

### 7-1. `--rebuild-from T3` で仮想テーマ指数 171 本が SQLite 範囲だけで再計算される（2026-09-26・5-5 で観測）

- **事象**: sandbox の `--rebuild-from T3` 後、単調移行中の `rs_value_e200`・`rs_roc_ema_63` が 67 → 238 件に増えた。差の 171 件は再計算ログの `no_saved_rows=171`（仮想テーマ指数）と一致
- **原因（推定）**: 仮想テーマ指数の T3 が Parquet 基点ではなく SQLite の保持範囲だけで再計算され、窓の先頭がウォームアップ（NULL）になる。ログ文言「価格履歴自体がSQLiteの保持期間に収まるため…正確です」は仮想テーマ指数には当てはまらない
- **判断**: 本計画の変更とは無関係（再計算経路には触れていない）。既存 issue「仮想テーマ指数のT3全期間再計算で、SPY参照データの供給不足…」と同じ領域のため、そこへ追記した（5-6）

### 7-2. フォールバック（判別不能）経路の誤差は EMA 系全般に出ている（2026-09-26・5-5 で観測）

- **事象**: 5-5 の照合で、`warmup_undetermined` でフォールバックした 245 銘柄中 208 銘柄が、`ema_150`・`ema_200` 等で Parquet 基点の値と不一致（相対差 1e-3〜1e-4 程度。例 ETHA `ema_150` 17.1257 → 17.1432）
- **原因**: SQLite の 504 本の先頭から EMA をシードし直すため、全履歴でのシードと値がずれる（§1.4 と同じ構造）
- **判断**: 案 C（Parquet 基点化）の必要性を補強する事実として、5-6 の起票に含めた。本計画のスコープ外
