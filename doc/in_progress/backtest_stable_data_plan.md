## 1. 背景と目的

バックテスト・最適化・シナリオバッチは、本番の Parquet マスターの**その時点の最新世代**を読む。
daily update は1日に2回新しい世代を作るため、次の問題がある。

| 実行形態 | 読み込み | 問題 |
| :--- | :--- | :--- |
| 単発のバックテスト・Optuna 最適化 | 開始時に1回だけ読み込み、メモリに保持 | 実行中の混在は無い。ただし、**どの世代で回したかの記録が残らない** |
| シナリオバッチ（`run_scenario_batch.py:346`） | 子プロセスがそれぞれ別のタイミングでポインタを読む | **実行中に daily update が走ると、run ごとに別の世代で比較する**。エラーは出ない |
| 比較全般 | — | 「新旧比較は同じ世代で」（rules §10.4）を、実行者の注意でしか守れない |

**目的**: バックテスト系は、既定で「**検証済みの最新バックアップ**」を読むようにする。
バックアップは中身が二度と変わらないので、daily update の影響が経路ごと無くなり、比較のデータもそろう。

### 着手前のベースライン（2026-09-25 実測）

- `data/_bk_*` は8本。自動で削除する処理は無い（削除は手動のみ）。
- Parquet を含むバックアップは、`BACKUP_MANIFEST.json` の `parquet_generation` キーで判別できる（`_bk_20260909_233905` のように DB だけのものもある）。
- 🔴 **バックアップ内の `latest_master.json` は、本番 `data/parquet_master/` のファイルを絶対パスで指している**。
  これをそのまま `get_latest_master_files()` に渡すと、**バックアップではなく本番を読む**（prune 済みなら失敗する）。
  バックアップ内のファイルは、`BACKUP_MANIFEST.json` の `parquet_generation`（ファイル名だけ）をバックアップのフォルダ基準で解決して読む必要がある。
- 2026-09-25 に、昇格後の世代 `20260925_135558` のバックアップを取得した（§5 の手順0）。

## 2. スコープと設計判断

### 2.1 変更すること

- **A.** バックアップから Parquet を読む関数を新設する（manifest 基準でパスを解決する）。
- **B.** `preload_data()` が「どのデータを読むか」を引数で受け取れるようにする。既定は最新のバックアップ。
- **C.** 3経路（`backtest_runner` / `optimization_runner` / `run_scenario_batch`）を、開始時に1回だけ参照先を決める形にそろえる。シナリオバッチは、親で決めたパスを子に渡す。
- **D.** 参照先を**開始時に表示**し、出力（結果 JSON・Optuna の study の属性・シナリオ出力）に記録する。
- **E.** バックアップが1本も無い環境では、警告を出して本番の最新世代を開始時に固定する（従来と同等）。
- **F.** 「Parquet を含む最新のバックアップは削除しない」というルールを文書化する。

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 |
| :--- | :--- |
| ハードリンクで世代を押さえる | **やらない**。バックアップは中身が変わらず、自動削除も無いため不要（ユーザー判断 2026-09-25） |
| バックアップの自動取得（昇格後・週次） | **やらない**。取得は手作業（ユーザー判断）。鮮度は、開始時に参照先の日時を表示して実行者が判断する |
| Parquet の丸ごとコピー | **やらない**。バックアップが既に実コピーなので、二重になる |
| バックアップ形式の変更（ポインタを相対パスにする等） | **やらない**。既存の8本と互換を保つ。読む側で manifest を使う |
| バックアップの Parquet をハードリンクで取る（容量節約） | **本計画に含めない**。バックアップの設計の話なので、必要なら別項目 |

## 3. 変更内容

### 3-A. バックアップの解決（`backend/pipeline/parquet_cache_manager.py`）

- `find_latest_parquet_backup(data_dir) -> str | None` — `data/_bk_*` のうち、`BACKUP_MANIFEST.json` に `parquet_generation` を持つものを、フォルダ名の日時で新しい順に探す。
- `get_backup_master_files(backup_dir) -> dict` — manifest の `parquet_generation` の各ファイル名を `backup_dir` 基準で解決して返す。**ファイルが1つでも欠けていたら例外**（本番パスへ黙って戻らない）。
- どちらも読み取りだけで、書き込みは無い。

### 3-B. `preload_data()` の参照先の指定

- 新しい引数 `data_source`。値は次のいずれか（2026-09-26 改訂。§7-3）。
  - `"backup"`: 本番 data ディレクトリの最新バックアップ（3-A）。無ければ警告を出して `"latest"` に切り替える（2.1-E）
  - `"latest"`: **現在の data ディレクトリ**（`paths.get_data_root()`。本体なら本番、ワークツリー・sandbox なら自分のデータ）の最新世代。変更前の `preload_data()` と同じ参照先
  - バックアップのフォルダ名（例: `_bk_20260925_...`）: そのバックアップ
- **既定値**: 現在の data ディレクトリが本番なら `"backup"`、そうでなければ `"latest"`（`paths.is_production()` で判定）。
  ワークツリー・sandbox でのバックテストは、再計算したデータを評価するのが目的なので（rules §10.4 Case 2）、自分のデータを読む。
- 解決後のファイル辞書を直接受け取る経路も持つ（シナリオバッチの子プロセス用）。
- `--refresh-cache`（SQLite から再生成する経路）は `"latest"` のときだけ許可する。バックアップへは書き込まない。

### 3-C. 3経路の統一

- `backtest_runner.py` / `optimization_runner.py`: CLI 引数 `--data-source` を追加し、`preload_data()` に渡す。
- `run_scenario_batch.py`: **親で1回だけ参照先を解決**し、ファイル辞書を子プロセスに引数で渡す。子はポインタもバックアップも探さない。

### 3-D. 表示と記録

- 開始時のログに、参照先の種類・バックアップ名（または世代名）・価格データの最終日を1行で出す。
- 記録先:
  - バックテスト結果 JSON
  - Optuna の study の `user_attrs`（例: `data_source`、`parquet_generation`）
  - シナリオ出力のメタ情報

### 3-F. 文書

- `doc/backend_specification.md` のバックテスト節に、参照データの既定と引数を追記する。
- `tools/backup_production_data.py` の docstring に「Parquet を含む最新のバックアップはバックテストの既定参照先。削除しない」を追記する。
- `/cleanup` の棚卸しで古いバックアップの削除を提案するときは、最新を対象外にする旨を追記する。

## 4. ユーザー確認事項

判断済み（2026-09-25）:

1. バックアップの取得は手作業。参照先の日時は開始時に表示する。
2. バックアップが無い環境では、警告を出して本番の最新世代を開始時に固定する。
3. 昇格後のバックアップを取っておく（手順0で実施済み）。

4. **既定値は `"backup"`**（2026-09-25 確定）。最新の数日分を使いたいときは `--data-source latest`。**本番以外（ワークツリー・sandbox）の既定は `latest`**（§3-B・§7-3。2026-09-26 オーケストレーター判断）。
5. **データが違う既存 study は、古い方をリネームして退避する**（2026-09-25 ユーザー案で確定）。
   - study 名は戦略名そのもので、`run_scenario_batch.py` がこの名前で最良パラメータを引く。そのため**新しいデータの study が正式名を持ち、古い方を別名に退避する**。
   - 開始時に、正式名の study の `user_attrs["parquet_generation"]` と今回の参照先の世代を比べる。違えば、古い study を `<戦略名>__<旧世代>` に退避し、正式名で新規作成する。
   - Optuna にリネームの API は無いので、`optuna.copy_study()` で別名にコピーしてから元を `delete_study()` する。`optimization_trials.db` はユーザー資産なので、**退避の前にファイルのバックアップを取る**（rules §10.1）。
   - 記録の無い既存 study（本機能の導入前に作られたもの）は、退避せず、今回の参照先を記録して引き継ぐ。昇格後に回している再最適化（5-18）の結果を消さないため。ログに警告を1行出す。

## 7. 途中発生した課題

- **7-1. 本番の旧世代は自動でも削除される（2026-09-26 判明）** — `parquet_cache_manager.clean_old_parquet_versions()`（最新2世代を残す・15分の猶予）がパイプラインから呼ばれる。方針議論で「prune は手動のみ」と説明したのは誤り。
  影響するのは本番で `--data-source latest` を指定したときだけ（開始時に固定した世代が、2回の daily update 後に消えうる。シナリオバッチの子が後から読むと失敗する）。既定の `backup` は影響を受けない。
  対応: 本番で latest を指定したときに「長時間の実行では世代が削除されうる」旨を警告ログに出す（3-B に含める）。
- **7-3. 計画の穴: ワークツリー・sandbox で本番を読んでしまう（2026-09-26・G2 不合格1回目）** — 3-B の初版は `"production"` を「本番 data ディレクトリの最新世代」と定義していた。
  変更前の `preload_data()` は「現在の data ディレクトリ」を読んでいたので、ワークツリーで T3 を再計算して merge 前に評価する経路（rules §10.4 Case 2）で、**再計算したデータではなく本番を評価する**ことになる。既定の `backup` も本番のバックアップを読むため、同じく評価できない。
  対応: `"production"` を `"latest"`（現在の data ディレクトリの最新世代）に置き換え、既定値を「本番なら backup、それ以外なら latest」にした（§3-B）。
- **7-4. scenario 系2ファイルへの `"backup"` 固定を撤回（2026-09-26）** — ワーカーは `scenario_runner.py` / `scenario_comparison_runner.py` の `preload_data()` に `data_source="backup"` を固定した。
  理由は `--mode read` のワークツリーで `test_scenario_comparison.py::test_run_comparison_generates_outputs` が落ちたことだが、これは rules §10.3 に記載の既知の環境要因で、回帰ではない。
  固定すると、ワークツリーで T3 を再計算したあと型3シナリオで評価しても本番を読むことになり、§7-3 の穴が再発する。main と同じ呼び出し（既定値の判定に任せる）に戻した。
- **7-2. ワーカー報告の失敗1件は環境要因** — `test_scan_price_anomalies.py` の `UnicodeEncodeError` は `PYTHONIOENCODING=utf-8` 無しで実行したため。付ければ 19 passed。
