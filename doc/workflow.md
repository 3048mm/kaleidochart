# 開発ワークフロー — ゲートと介入地点

開発項目を**計画 → 実装 → 検収 → 取り込み → 昇格 → 撤収**と進めるときの、
ゲート（通過条件つきの関門）・判断者・ループ上限・閾値を定義する。

> [!IMPORTANT]
> **ゲート・判断者・数値の定義はこの文書だけに置く。**
> CLAUDE.md・`.claude/commands/`・`.claude/agents/`・`doc/agent_execution_rules.md` は
> ここを参照するだけで、同じ数値や条件を書き写さない（書き写すと食い違う。
> 2026-09-23 時点で5件の重複と1件の矛盾があった: `doc/completed/workflow_gates_plan.md`）。

---

## 1. ゲート表

| ゲート | 判断者 | 通過条件 | 実行手段 |
| :--- | :--- | :--- | :--- |
| **G1 計画合意** | **ユーザー** | 計画書 §4「ユーザー確認事項」に合意 | `/start-item` |
| G2 項目検収 | オーケストレーター | テスト全件 pass ＋ 計画書の受け入れ条件と照合済み | `/accept` |
| G3 ブランチレビュー | オーケストレーター＋`/code-review` | 未対応の重大指摘が0件（§3 の上限内） | `/accept`（ブランチ完了時に**自動**） |
| **G4 merge** | **ユーザー** | 人のレビュー（G3 の記録を材料にする） | ユーザーが `git merge` |
| **G5 昇格**（種別 B / C のみ） | **ユーザー**が実行を承認 | health check 合格 | `tools/deploy_after_merge.ps1`（B）／バックアップ＋in-place マイグレーション（C） |
| G6 撤収 | オーケストレーター（**ユーザーの指示で**実行） | 本番データが無傷であることを実測 | `/cleanup` → `tools/remove_worktree.ps1` |

- 変更種別 A〜D の定義: `doc/agent_execution_rules.md` §10.2
- ワークツリーのデータ準備（G1 の後・実装の前）: 同 §10.3
- バックテスト評価は G4 の前に行う: 同 §10.4

```
G1 計画合意 ──▶ 実装 ⇄ G2 項目検収（チェック項目ごと）
                          │ 実装系の項目がすべて完了
                          ▼
                G3 ブランチレビュー（自動・上限2周）
                          │ 「merge 可能」と報告
                          ▼
                G4 merge ──▶ G5 昇格（B/C のみ） ──▶ G6 撤収
```

## 2. 介入地点 — ユーザーが判断するのはどこか

**ユーザーが判断するのは G1 / G4 / G5 と、§2.1 のエスカレーション条件だけ**。
それ以外はエージェントで完結させ、途中でユーザーに確認を求めない。

エージェントが**聞かずに進める**もの:

- G2 / G3 の実行（G3 はユーザーの指示を待たずに起動する）
- レビュー指摘の仕分け（対応 / issue 化 / 却下）と、それに伴う計画書の更新・再委譲
- 計画書のチェックリスト・作業中メモ・レビュー記録の更新
- G2 合格後の、ワークツリー内の自ブランチへのコミット（オーケストレーターが行う。ワーカーはコミットしない。`doc/agent_execution_rules.md` §7）

### 2.1 エスカレーション条件（どのゲートでも、該当したら止めてユーザーに上げる）

1. §3 のループ上限を超えた
2. 設計判断・仕様の解釈が必要になった／計画に穴があった
3. 破壊的操作が必要になった（本番データ・ユーザー資産 DB・未コミット変更の破棄・未マージブランチの撤収）
4. 原因を説明できないテストの赤（既知の環境要因は `doc/agent_execution_rules.md` §10.3）

上げるときは「何が起きたか・試したこと・選択肢と推奨」をまとめて1回で伝える。

## 3. ループ上限・閾値

> [!NOTE]
> 「根拠」欄が暫定のものは、**運用しながら調整する前提の値**である。
> 「多すぎて読まれない」「見逃した」のどちらかが起きたら見直し、この表だけを直す。

| 項目 | 値 | 根拠 |
| :--- | :--- | :--- |
| 同一エラーのリトライ | 3回で打ち切り | ユーザー設定（手順: `doc/agent_execution_rules.md` §4 / §4.1） |
| G2 不合格 → 計画書更新して再委譲 | 2回まで。3回目の不合格でエスカレーション | **根拠なし・暫定**（2026-09-23） |
| G3 レビューの往復 | 2周まで。2周目の後も未対応の重大指摘が残ればエスカレーション | 暫定。t3_incremental で2周を要した1例のみ（2026-09-23） |
| G3 の対象 | 種別 B / C は必須。種別 A は**変更 200行 または 5ファイルを超えたら**必須。それ以外の A と D は対象外 | **根拠なし・暫定**（2026-09-10 設定） |
| G3 のレビューレベル | 種別 B / C は `high`、種別 A は `medium` | **根拠なし・暫定**（2026-09-23） |
| G3 のユーザー報告 | 上位3件まで・重大度つき | 絞らないと読まれなくなり、無いより悪い（`doc/issue_list.md` P3） |

### 3.1 G3 の「上位3件」は報告の上限であって、対応の上限ではない

**重大な指摘は件数に関係なく全件を仕分けて対応する。** 3件に絞るのはユーザーへの報告だけで、
全件は計画書の「レビュー記録」に残す。
（文言どおり3件で打ち切ると、market_breadth_indicators の実例では重大4件のうち1件を落としていた）

レビューで狙うのは「**実装もテストも通るが意図を満たしていない**」型（呼んでいるが効いていない、
仕様書とのずれ、共通関数の再実装、隔離の前提を壊す書き込み）。テストで検出できる種類は対象外。

## 4. 規則の置き場所

新しい規則を足すときは、性質で置き場所を決める。同じ規則を2箇所に書かない。

| 規則の性質 | 置き場所 |
| :--- | :--- |
| 機械的に判定できる（コマンドの形・パス） | hook（`tools/hooks/`、登録は `.claude/settings.json`） |
| 役割の縛り（ワーカーがやってよいこと・報告項目） | `.claude/agents/` |
| 手順（何をどの順で実行するか） | `.claude/commands/` |
| ゲート・判断者・数値 | **本書** |
| 背景・理由・事故例・エラー回避策 | `doc/agent_execution_rules.md`（汎用）／`doc/project_knowhow.md`（stocktool 固有） |
| ドメイン手順（sandbox・SQLite・Parquet 等） | `.claude/skills/` |
| 毎セッション必要な索引・絶対禁止事項・プロジェクト知識 | `CLAUDE.md` |
