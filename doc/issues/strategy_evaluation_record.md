  - **🔴 見極めるべき点（ユーザー判断 2026-09-05: まだタスクにしない）**:
    **作業手順に紐づかないと形骸化する類の仕組み**である。
    「気が向いたら書く」運用にすると数ヶ月で嘘の混じった古い表になり、
    **無いより悪い**（読んだ人が古い数値で判断する）。導入するなら
    「シナリオバッチを回したら結果をカルテに追記する」のように
    **既存の作業手順の一部として強制される形**にできるかが条件。
    それが設計できないなら**採らない**判断もありうる。
  - **併せて考えるべき論点**:
    - 誰が書くか（人間 / エージェント）。エージェントに書かせるなら CLAUDE.md への規約追加が要る
    - 自動生成できる部分（型1 study のベスト値・型3の集計）と、手で書く部分（所見・教訓）の切り分け。
      自動化できる部分が多いほど形骸化しにくい
    - 計画書の §6「検証プラン / 結果」との重複をどう解消するか（二重管理は形骸化の典型的な入口）
  - **同じ問題が戦略評価以外でも起きた（2026-09-07 追記）**:
    ワークフロー棚卸しの作業中、会話上で確定した**14項目の改善バックログ**が
    どこにも永続化されない状態になった。issue_list に入れるほど確定しておらず、
    計画書はまだ存在しない段階の成果物で、**置き場が定義されていない**。
    実際に計画書へ転記する際に1項目（反証欄・P0 相当）を落とし、
    たまたま追跡表を作ったことで気づいた。
    - **判明したこと**: これは「戦略評価の置き場」ではなく、より一般に
      **分析フェーズの中間成果物（計画書ができる前の成果物）に置き場が無い**問題である。
      戦略カルテはその一種にすぎない。**設計するならこの粒度で考えること。**
    - **記憶の層は3つあり、欠けているのは3層目だけ**:
      ①セッション横断の永続知識（CLAUDE.md / rules / knowhow / skills）＝ 強い、
      ②確定タスクの引き継ぎ（`doc/in_progress/*_plan.md`）＝ 機能している、
      ③**分析フェーズの中間成果物 ＝ 会話コンテキストのみ**
    - **軽い側の対策は先行実施**: 「転記したら元と件数を突き合わせる」は
      `doc/in_progress/workflow_harness_cleanup_plan.md` §3-F-2 でテンプレートに入れる。
      置き場そのものの設計（重い側）は本 issue に残す
    - **参考**: [ハーネス設計の原則](https://www.anthropic.com/engineering/harness-design-long-running-apps) は
      「コンパクション」より**コンテキストリセット＋構造化ハンドオフ**を推奨し、
      ファイルベースの構造化されたコンテキスト受け渡しを中核原則として挙げている。
      当プロジェクトの計画書は②としてはこれを満たしているが、③には器が無い
  - **関連**: P2「スクリーナー戦略の『退役』運用を定める」——
    「なぜ機能しなかったかの記録をどこに残すか」を決める必要があるという点で**同じ問題の別の面**。
    片方だけ決めると置き場が2つに割れるので、**両方まとめて設計すること**
