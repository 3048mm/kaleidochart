# バックエンドデータ検証仕様書 (Backend Verification Spec)

## 1. 目的
本ドキュメントは、株価データおよびインジケーター情報の正確性、完全性、一貫性を維持するための検証項目と、異常発生時の復旧手順を定義する。

---

## 2. 検証基本方針

### 2.1 機能追加・変更時のフロー
- 新規機能追加時は、本仕様書に **単体検証仕様** を追記し、それに基づいた単体検証を実施すること。
- 変更内容に応じて、影響範囲のある既存機能に対しても単体検証を再実施すること。
- 原則として、全ての検証は **サンドボックスDB** (`stocktool_sandbox.db` 等のコピー) を用いて行うこと。本番 DB への直接的な変更を伴う検証は禁止する。

### 2.2 DBスキーマ変更時のフロー
- DBキーの追加・削除・型変更を伴う場合は、まずサンドボックスDBでスキーマが正しく更新されていることを確認する。
    - **バックアップの取得**: 変更前に、サンドボックスDBのバックアップを必ず取得しておくこと（失敗に備えるため）。
    - **リカバリと再検証**: スキーマの変更に失敗した場合は、バックアップからオリジナルの状態へ復元し、再度キー追加等の手順を最初から検証すること（本番環境での失敗を未然に防ぎ、手順を確立するため）。
- スキーマの整合性確認が完了した後に、それを使用するロジックの単体検証を実施すること。

### 2.3 テスト駆動開発 (TDD) ルール
- **テスト先行**: 機能追加・変更時は、先にテストコード（`backend/tests/test_*.py`）の追加・修正を行い、テストが失敗（Red）することを確認してから実装に着手する。
- **全件パスの確認**: コードの変更をコミットする前に、以下のコマンドをローカルで実行し、全テストがパスすることを確認する。
  ```powershell
  $env:PYTHONPATH="backend"; python -m pytest backend/tests/ -v
  ```
- **適用範囲**: TDDルールは今後の新規機能から適用する。既存コードへのテスト追加は、改修のタイミングで段階的に行う。

## 3. DB変更時（キー追加・変更等）の具体的検証項目

### 3.1 スキーマ整合性とデータ継続性
- [ ] `models.py` の変更が物理 DB (`stocktool.db`) に反映されているか。
- [ ] **既存データのカラム健全性**: 新規追加されたカラムが、既存レコードで期待通り（デフォルト値または計算値）に埋まっているか。
    - 検証方法: `db_health_check.py` に対象カラムを指定し、NULL レコード率が 0% であることを確認。

### 3.2 データパイプライン検証 (Pipeline Verification)
- [ ] **フェーズ別キャッチアップ**:
    - `T2.MAX(date) > T3.MAX(date)` の際、T3 が差分期間（MAX+1〜今日）を自動算出・保存し、最終的に T2 と最新日が一致すること。
    - `T3.MAX(date) > T4.MAX(date)` の際、T4 が不足日付分のランキングを一括生成（Delete-Insert）し、T3 と最新日が一致すること。
- [ ] **再試行の安全性 (Idempotency)**: 改修後の `update_pipeline.py` を重複実行した際、`IntegrityError` が発生せず、最新データが正しく維持されること。
- [ ] **SPY ブロックの先行性**: T3 計算において、SPY の `sma_200` 等が他銘柄より先に計算され、RS計算に利用可能になっていること。
- [ ] **新規銘柄バックフィル**: T1 で新規追加されたばかりの銘柄に対し、T2/T3 が過去 5 年分を一気に取得・計算し、既存銘柄と足並みが揃うこと。

## 復旧・デバッグ時の注意

- **暫定的なハードコードの禁止**: 復旧作業やデバッグのために一時的にコード（日付フィルター、特定のシンボルのスキップ等）を書き換える場合、そのコードを本体（`main` / `master` 相当）のロジックに含めてはならない。
- **復旧専用プロセスの分離**: 大規模なデータ修復が必要な場合は、本体のパイプラインに条件分岐を追加するよりも、復旧専用の使い捨てスクリプト（`rebuild_xxx.py` 等）を作成して実行することを推奨する。
- **設定値の外部化**: どうしても挙動を制限する必要がある場合は、`.env` や設定ファイル、あるいは実行時引数を介して制御し、ソースコード自体を汚染しないこと。

## 4. データ欠損・不整合発見時の復旧手順方針

### 4.1 復旧フロー
1. **影響範囲の特定**: `db_health_check.py` 等を用いて、どの期間・どの項目・どの銘柄に欠損があるか特定する。
2. **データの巻き戻し (Rollback)**: 不整合が疑われる期間の T3 (指標) / T4 (ランク) / T5 (シグナル) を削除する。
    - ※ T2 (価格) は API から再取得可能なため、必要に応じて削除。
3. **基準データ (SPY) の再構築**: まず SPY のインジケーターを全期間再計算し、NULL がないことを確認する。
4. **全銘柄の再構築**: `--re-calculate` フラグを使用し、最新ロジックで全件再生成を行う。

### 4.2 復旧時の検証項目 (データ品質基準)
- [ ] **行数一致**: `T2 行数 == T3 行数` であること（全銘柄対象）。
- [ ] **項目レベルの完全性 (Column-level Quality)**:
    - [ ] `sma_200`, `ema_21`, `relative_strength_spy` 等、計算の核となる列に **NULL が 1 件も含まれていないこと**。
    - [ ] **RS Ratio/Rank の分布確認**: ランク (T4) が 0.0〜1.0 の範囲に均等に分布しているか（特定値への偏りがないか）。
- [ ] **T5 連続性**: 市場シグナルが直近5年間、欠損なく連続しているか。
