## 3. 変更内容

### 3.1 検査A: 上流の自己矛盾

**何を**: 上流が `splits` に記録している分割日で、上流自身の調整済み終値に
分割比ぶんの段差が残っていないかを見る。

**なぜ**: 遡及適用が正しく行われていれば、分割日に段差は出ない。
段差が `1/factor` と一致すれば、**上流は分割を知っているのに適用できていない**。

```
判定: jump = close[分割日] / close[分割日の前営業日]
  jump ≈ 1.0        → 適用済み（正常）
  jump ≈ 1/factor   → **未適用**（上流が壊れている）
  それ以外          → 判定不能（実際の値動きと混ざっている可能性）
```

**対象**: `backend/scripts/scan_split_consistency.py`

**影響範囲**: 新規スクリプトのため既存動作への影響なし。

### 3.2 検査B: 手元と上流のスケール乖離

**何を**: 重複期間で `手元/上流` の中央値を取り、1.0 から乖離していたら報告する。
乖離幅が分割比（0.5 / 2.0 / 1.5 等）に一致する場合は**強い警告**にする。

**なぜ**: 2026-09-04 に実際に効いた検査。5銘柄すべてがこれで浮かび上がった。
どちらが正しいかは判定せず、**両方の値と、判断材料（分割履歴・配当の有無）を並べる**。

**配当調整の扱い**: 当プロジェクトは `auto_adjust=True` で配当調整も入るため、
配当銘柄では乖離があって当然。**無配当銘柄で乖離があれば分割の疑いが濃い**
（＝第2段階の「無配当銘柄チェック」を検査Bに統合する）。

### 3.3 取得方法

`yf.download(tickers=[...], start=..., actions=True, group_by='ticker')` で
**価格と分割イベントを1回の呼び出しで**取る。銘柄ごとに `Ticker().splits` を
叩くと 3,000回超の呼び出しになるため。

バッチサイズと待機は T2（`t2_prices.py`）の実績値に合わせる。

### 3.4 週次への組み込み（**本計画ではやらない**。将来組み込む場合の設計）

§4-2 の判断により本計画のスコープ外。組み込む判断になったときのために設計だけ残す。
`run_sec_corporate_action_sync()` と同じ形にする。

```python
def run_split_consistency_scan(dry_run: bool, report_dir: str) -> dict:
    try:
        from scripts.scan_split_consistency import run as scan_run
        return scan_run(report_dir=report_dir)
    except Exception as e:  # noqa: BLE001 — 週次メンテ全体を巻き込まない
        logger.error(f"分割整合スキャンに失敗しました（週次メンテは続行します）: {e}")

**失敗しても週次メンテ全体を落とさない。** ネットワーク依存であり、ここで例外を

### 6.1 反証 — この結論が誤りだとしたら、何が観測されるはずか

- **この結論が誤りだとしたら観測されるはず**:

  本計画の主張は「**上流の自己矛盾を見れば MNST 型を検出できる**」。
  これが誤りなら、次のいずれかが観測される。

  1. **上流が分割記録すら持っていない銘柄で価格が壊れている** — 検査Aは
     「記録された分割日」を起点にするので、記録が無ければ**何も見ない**。
     `SOXS` / `UAVS` など299件が該当（skill §6 限界1）。
     **これは本計画では原理的に検出できない。** 第3段階（外部ソース）の担当
  2. **手元と上流が同じ誤りを共有している** — 検査Bは両者の差を見るので、
     両方が同じスケールで壊れていれば**一致してしまい素通りする**
  3. **上流の値が実行中に変化する** — 2026-09-04 に実際に起きた
     （MNST は12:00に27.81→14:44に13.90、APH は逆方向）。
     同じ銘柄を2回スキャンして違う結果が出るなら、判定そのものが不安定

- **独立経路での確認**: **未実施**。着手時に以下を行う。

  - **実価格からの逆算**（外部ソース不要の独立経路）: 検出した銘柄について
    「2018年の実勢価格 ÷ その後の累積分割比」を計算し、手元・上流のどちらと
    一致するかを見る。MNST は `55.6 / 4 = 13.90` で手元と一致した
  - **配当調整幅の定量検算**（同上）: 配当・分配金から調整係数を概算し、

### 6.3 対象期間の決定（§4-3 の判断根拠・2026-09-10 実測）

2年と全期間の両方を 2,956銘柄に流して比較した。

| 期間 | 検査A | 検査B | 実行時間 |
| :--- | ---: | ---: | ---: |
| **2年（既定）** | 0件 | 0件 | 約9分 |
| 全期間（`--years 20`） | 2件（**いずれも影響なし**） | **0件** | 約22分 |

**検査Bは全期間でも0件**。手元データは全重複期間で上流と一致している。
全期間で増えたのは、**手元が保有していない期間**の上流側の破損だけだった:

```
CHT    2008-10-15 ×1.21       手元の保有は 2017-01-03 以降
FWONA  2016-04-18 ×1.423988   同上
```

→ **既定2年で確定。** 理由:

1. **実害のある差分がゼロ** — 全期間にしても検査Bは何も追加で見つけない
2. **対応不能な警告が増える** — 保有期間外なので直しようがなく、毎回鳴り続ける。
   警告の常態化はレポートが読まれなくなる原因で、週次組み込みを見送った理由と同じ
3. **時間が2.4倍** — 得るものがないのにコストだけ増える

`--years` は残す。充足で過去を足した直後の検証など、棚卸し用途で使う。

## 7. 途中発生した課題

### 7.1 判定を3値で設計していたが VISN が漏れる（設計変更）

計画時は `ok` / `split_suspect` / `unknown` の3値を想定していたが、テスト作成中に
**VISN（比 1.7541）が分類できない**ことに気づいた。分割比ではないが、乖離72%を
`ok` に丸めるのは誤り（実際に手元が古く、修正が必要だった）。

→ **`divergent` を追加して4値にした。**
**「分割比に一致しない」ことは「正常」の証明ではない。**

### 7.2 株式配当を分割の未適用と誤検出していた（**実装バグ・修正済み**）

ユニバース全体（2,956銘柄）に流したところ検出18件。内訳を見ると
**16件が誤検出**だった。

```
HON   2025-10-30 factor=1.061   SCCO  2024-11-06〜2026-08-11 factor=1.006〜1.012（7件）
J     2025-05-16 factor=1.01    TR    2025-03-05 / 2026-03-05 factor=1.03（2件）
LEN   2025-01-21 factor=1.033   METC  factor=1.01 / 1.014（2件）
SNFCA 2025-07-11 / 2026-07-10 factor=1.05（2件）
```

いずれも**分割ではなく小額の株式配当**（`TR` = Tootsie Roll の年3%株式配当など）。

**原因は判定順序。** `factor=1.01` だと「未適用」の期待値 `1/1.01 = 0.990` と
「適用済み」の `1.0` が許容幅（±8%）の中で**完全に重なる**。先に評価していた
「未適用」が常に当たっていた。

**修正**: `MIN_DISCRIMINABLE_GAP = 0.15` を導入し、`|1/factor - 1|` がこれ未満なら
**判定を放棄する**（`unknown`）。2つの仮説が識別できない領域で判定してはいけない。
テストで固定した（`test_tiny_stock_dividends_are_not_reported_as_unapplied`、
`test_a_real_split_is_still_detected_after_the_fix`）。

> [!NOTE]
> **この誤検出は「ユニバース全体に流して誤検出率を見る」という §6 の検証項目が
> なければ素通りしていた。** 5銘柄のテストだけでは出なかった。

### 7.3 本物のデータ破損を2件検出した（**本計画の成果**）

誤検出を除いた残り2件は**いずれも本物**だった。

| 銘柄 | 分割 | 手元/上流の比 |
| :--- | :--- | ---: |
| `IESC` | 2026-08-24 ×2.0 | 2.0000 |
| `WLFC` | 2026-07-21 ×3.0 | 3.0208 |

**上流を正解と仮定せず**、手元データ自身の段差という独立経路で確認した:

```
IESC  2026-08-21   685.04
      2026-08-24   324.12   段差 0.4731   ← 1/2.0 = 0.50
WLFC  2026-07-17   191.65
      2026-07-20    63.12   段差 0.3294   ← 1/3.0 = 0.333
```

**実在の価格系列が1日で半分・1/3になることはない。** 分割日に新スケールの行が
継ぎ足され、過去が古いスケールのまま残っている
（`upstream-data-diagnosis` §6「限界3: 日次の差分取得では過去の調整が反映されない」）。

`WLFC` は分割日の前営業日（07-20）で飛んでいる。ex-date と yfinance の
記録日が1日ずれるケース。**補正の `--before` は記録日ではなく実測の段差日で
指定すること。**

**この2件は既存の仕組み（週次の `scan_price_anomalies.py`）が見逃していた。**
なぜ見逃したかは §8 に残作業として記載。

### 7.4 `scan_price_anomalies.py` は検出していたが「分類」で捨てていた

§7.3 の2件を既存の週次検査がなぜ見逃したかを調べたところ、
**検出漏れではなく分類の問題**だった。両方ともレポートに**入っていた**:

```
IESC  2026-08-24  ratio=0.4731  same_day_count=4  → market_wide
WLFC  2026-07-20  ratio=0.3294  same_day_count=1  → real_move
```

`IESC` は「同日に4銘柄が飛んだ」ため市場全体の動き、`WLFC` は「単独だから」
実際の値動き、と分類されて落ちていた。

**その4銘柄の正体を確かめたところ、無関係な分割が重なっただけだった:**

| 銘柄 | 比 | 分割記録 |
| :--- | ---: | :--- |
| `AVB` | 0.370 | **2026-08-17 ×2.793** |
| `IESC` | 0.473 | **2026-08-24 ×2.0** |
| `FLZH` | 0.228 | なし |
| `FBDT` | 0.514 | なし |

`AVB`（AvalonBay、大型REIT）が1日で63%下落することはない。
**`MARKET_WIDE_MIN_SYMBOLS = 4` は、同日に4件の分割が重なると全部を
「市場全体の動き」として消してしまう。**

これは 2026-09-04 の `auto_adjust=False` 事故で 2018-04-02 が `market_wide` に
分類されたのと**まったく同じ失敗の型**（実際に -2.2% の日だった）。

#### 分類の分布（全1,357件）

```
low_liquidity    613
real_move        475
market_wide      220
virtual           48
split_suspect      1   ← **1件だけ**
```

直近1年で **比 0.6未満 / 1.8超なのに `market_wide` か `real_move` で落とされたものが
118件**ある。**分類が過剰に捨てている。**

#### 根本原因

**分類器が分割メタデータを一切見ていない。** 「その日に分割記録があるか」を
参照すれば `IESC` も `WLFC` も `AVB` も即座に分割と分かる。
比の大きさと同日件数だけで判断しているため、分割と実際の値動きを区別できない。

→ **修正は別タスク**（本計画は「検出手段を作る」まで）。§8 に記載。
本スキャンは分割メタデータを見るので、この穴を実質的に埋めている。

### 7.5 保有期間外の分割を報告していた（改善）

§6.3 の全期間スキャンで `CHT` / `FWONA` が検出されたが、いずれも

```

  CHT      2008-10-15 ×1.21

### 7.7 `IESC` / `WLFC` の補正を実施した（2026-09-10）

検出した2件を `adjust_symbol_split.py` で補正した。

```
IESC  --before 2026-08-24  --factor 0.5       --tolerance 0.08   2,422行
WLFC  --before 2026-07-20  --factor 0.333333                     2,397行
```

#### `--tolerance` を広げた理由（安全装置を緩める判断）

`IESC` は既定の接合部検算（±5%）で止まった:

```
実測比率 0.4731 / 申告 factor 0.5 (許容 ±5.0%)   → 5.38% 超過で中断
```

**闇雲に緩めず、0.4731 と 0.5 のどちらが分割比かを独立に確認した。**
上流（分割適用済み）の当日変化率を見ると:

| 銘柄 | 上流の当日変化率 | 理論値 `(1/factor)×(1+move)` | 手元の実測比 |
| :--- | ---: | ---: | ---: |
| `IESC` | **-5.37%** | 0.4731 | **0.4731** ✅ |
| `WLFC` | **-1.19%** | 0.3294 | **0.3294** ✅ |

**小数点4桁まで一致。** 分割比は 1/2・1/3 で正しく、差は分割日当日の
実際の値動きだった。`--factor 0.4731` を指定すると**当日の値動きを過去全体に
塗り込む**ことになる。

裏付けは3経路で独立している: ①上流の分割記録 ②スキャンの手元/上流比
（499行の中央値で厳密に 2.0000）③上記の分解。

> [!CAUTION]
> **`--tolerance` の既定値を恒久的に緩めてはいけない。** 本来止まるべき
> 係数の取り違えが通る。今回は銘柄限りで指定した。

#### `--before` は記録日ではなく実測の段差日

`WLFC` は上流の記録日（2026-07-21）と手元の段差日（2026-07-20）が1日ずれた。
ex-date と yfinance の記録日のずれ。記録日で指定すると**段差の残る行が1行できる**。

#### T3 の再計算は不要だった（確認済み）

`adjust_symbol_split.py` は T3・仮想テーマ再合成・T4・世代公開・SQLite反映まで
一貫して行う。**設計どおり動いたかをデータで確認した** — 分割日をまたぐ
`sma_50` が飛んでいなければ、移動平均の窓に入る過去50日が補正後の値になっている:

```
IESC  2026-08-21 close 342.52  sma_50 344.35
      2026-08-24 close 324.12  sma_50 343.52   段差 0.9976  ← 飛んでいない
WLFC  2026-07-17 close  63.88  sma_50  67.11
      2026-07-20 close  63.12  sma_50  66.78   段差 0.9951  ← 飛んでいない
```

SQLite ホットキャッシュも Parquet と一致。**追加の `--rebuild-from T3` は不要。**

> [!NOTE]
> `resync_price_scale.py` は逆に T3 以降を呼び出し側に委ねる設計。
> **1〜2銘柄をピンポイントで直すなら `adjust_symbol_split.py` が完結して速い。**
> 多数の銘柄を触った上で全体の T3 再計算を予定しているなら
> `resync_price_scale.py` + `--rebuild-from T3`（重い経路を二度通さない）。

#### 補正後の検証

```

db_health_check --all          →  要対応 0銘柄
```
