## 1. 背景と目的

`scan_split_consistency.py`（第1・2段階）は上流(yfinance)自身の自己矛盾と手元/上流のスケール
乖離を検出できるが、**上流が分割記録そのものを持たない銘柄は原理的に検出できない**
（`doc/issue_list.md` の元の記述では該当299件）。

> [!IMPORTANT]
> **本計画がカバーするのは299件全体ではない。** 実際に照合するのは、既存のヒューリスティック
> （`scan_price_anomalies.py` / `scan_split_consistency.py` の近傍不一致検出）が「怪しい」と
> 既に挙げている少数の候補（現状 `SOXS` 1件 + 近傍不一致8件）だけ。299件の大半は
> `real_move`/`low_liquidity`等に分類済みで、そもそも本計画のスキャン対象になっていない。
> **この計画を完了しても issue_list.md P1 を「全件解決」としてクローズすることはできない**
> （構造的なギャップが残る旨は §8 に明記する）。この計画の目的は「今ある少数の未決着候補に
> 決着をつけ、次に似た候補が出たときに使える照合スクリプトを資産化すること」に絞る。

### この計画で実際に分かったこと（2026-09-10〜11の調査で確定）

前回計画（初版）では「moomooが第3段階の独立ソースとして機能するか」自体が未確認だったが、
**実アカウントでの調査により以下が確定した**:

- 口座開設・入金は不要。moomooアカウント登録（SMS認証）+ OpenDインストールのみで利用可能
- 米国株LV3市場データ（Nasdaq Basic+TotalView, NYSE ArcaBook）は現在プロモーションで無料
- `get_rehab(code)` の検証: `US.AAPL` の既知5分割（1987/2000/2005年 ×2, 2014年 ×7, 2020年 ×4）と
  **日付・比率とも完全一致**。独立ソースとして信頼できることを確認済み
- **`SOXS`**: moomooに2026-03-05付 `split_ratio=20.0` の併合記録が実在。「上流に記録が無く
  観測比0.054から1:20と推定」だった件が**確定値になった**
- **`STKH`**: moomooも同じ2026-07-27に`split_ratio=3.0`を記録（yfinanceの記録と一致）。
  moomoo独自の実売買価格でも同じ2.667倍（11%外れた比）が再現され、**分割適用の不備ではなく
  実際の値動きが乗っていた**と判断できる材料が揃った。ただし §6.1 で後述するとおり、
  この2件はいずれも moomoo 自身から得た結論を moomoo で再確認しただけであり、
  独立性の観点では反証としてまだ弱い（要対応）
- `get_rehab` はヒストリカルK線クォータ（実測: 当日1回目は remain=300）を消費しない。
  レート制限（60req/30秒、エンドポイント別かは未確認・保守的に合算で実装）だけ気にすればよい

これを受けて `backend/data_collection/moomoo_client.py`（`MoomooClient` Wrapper）を実装し、
2026-09-11 に Opus アドバイザーレビューを受けて2件の是正（§7参照）を行った。
**本計画の残作業は、この Wrapper を使って候補ティッカーを実際に照合するスクリプトを作り、
未決着候補に決着をつけること。**

### 今回実施すること

#### 比の変換仕様（実装前に固定する）

moomoo の `split_ratio` と yfinance の `Stock Splits`（`scan_split_consistency.py` が
`factor` と呼んでいる値）は向き・単位が異なる可能性があるため、突き合わせ前に変換仕様を
明文化する。**実測で確認済みの対応関係**:

| 銘柄 | イベント | moomoo `split_ratio` | yfinance `factor` | 関係 |
| :--- | :--- | ---: | ---: | :--- |
| `AAPL` | 2020-08-31 (4:1 forward split) | 0.25 | 4.0 | `split_ratio == 1.0 / factor`（両方とも実測値） |
| `STKH` | 2026-07-27 (1:3 reverse split) | 3.0 | 1/3 ≈ 0.333 | `split_ratio == 1.0 / factor`（両方とも実測値） |
| `SOXS` | 2026-03-05 (20:1 reverse split) | 20.0 | 0.05 | `split_ratio == 1.0 / factor`（**yfinance側は未記録。0.05はmoomoo側の実測値から逆算した仮説であり、独立の実測ではない。関係式の検証としては循環している**） |

→ **`moomoo_split_ratio == 1.0 / yfinance_factor` で forward/reverse とも一貫する**
（独立の実測は `AAPL`/`STKH` の2件。`scan_split_consistency.py::detect_unapplied_split` の
`expected = 1.0 / factor` とも整合する＝`moomoo_split_ratio` は「その日の価格倍率」を
直接表している）。この関係を突き合わせロジックの起点にする。

#### 2種類の許容幅を混同しない

`scan_split_consistency.py` / `price_anomaly.py` には**性質の異なる2つの許容幅**がある。
今回作るスクリプトが使うのは**メタデータ同士の突き合わせ**であり、どちらも意味が違うので
流用しない（Opusレビューで指摘。当初案は `SPLIT_JUMP_TOLERANCE` を誤って想定していた）:

| 許容幅 | 用途 | 今回使うか |
| :--- | :--- | :--- |
| `SPLIT_JUMP_TOLERANCE`（0.08）/ `find_nearby_split` の境界値問題（`STKH`が0.08で不一致・0.12で一致） | **価格の実際のジャンプ**が分割比どおりかを判定する（ノイズを含む実測値 vs 理論値） | **使わない**。§2.2で「価格レベルの突き合わせは標準機能にしない」と決めた領分 |
| 日付の窓（`find_nearby_split`の`SPLIT_DATE_WINDOW_DAYS`相当、`WLFC`の実測1日ズレが前例） | 2つの**記録**（moomoo/yfinanceのex-date）が同一イベントを指しているかを日付で仮対応づけする | **使う**。まず流用可否を確認する |
| 比率の一致判定 | 対応づいた2つの**記録**の `split_ratio` 同士が一致するか | **使う。ただし新規に定義する**（メタデータ同士は本来ぴったり一致するはずなので、ノイズ前提の0.08ではなく数%程度のタイトな許容幅にする） |

**`STKH` はこのスクリプトの土俵では単純な一致ケースになる**: yfinance側の記録（1/3）と
moomoo側の記録（3.0）は変換仕様どおり一致するため、「一致」と判定されるだけで終わる。
**価格レベルで11%乖離していた事実（既に手動調査で確定済み、§1参照）はこのスクリプトの
検証範囲外**であり、再現しようとしない（§2.2の決定と整合させる）。

#### 実装ステップ（TDD、委譲する場合は1ステップ=1委譲単位を想定）

1. 既存 `scan_split_consistency.py` の `compare_scale()` / `is_split_like_ratio()` と、
   `price_anomaly.py` の `find_nearby_split()`（日付窓の付け方）の再利用可否を確認する
   （同じ判定ロジックを2箇所に書かない。ただし上記のとおり許容幅の値そのものは流用しない）
2. 両ソースの比の正規化関数（上記の変換仕様）とそのユニットテストを先に書く
   （red→green。`AAPL`/`STKH` の実測値をフィクスチャに使う。`SOXS`は循環参照のため
   このテストの正解データには使わない）
3. 突き合わせ判定（日付窓で対応づけ、比率のタイトな許容幅で一致/不一致/該当なしを判定する
   ロジック）を実装する（red→green）。**陽性対照・陰性対照・両ソースとも記録なしの3パターンを
   最初からテストに含める**（§6.1参照）
4. CLI（`--tickers` 必須）・CSV出力（**ワークツリーローカル**の
   `data/maintenance_reports/moomoo_verification_<timestamp>.csv`。本番 `data/` は
   `--mode read` プロビジョニングで読み取り専用のため、書き込みは常にワークツリー側になる。
   作業ブランチ節参照）を実装する
5. 実データで実行し、`SOXS`（moomoo側のみ記録あり、が正しく検出されること）・`STKH`（一致と
   判定されること）・残り候補（§4で範囲確定）を照合する
