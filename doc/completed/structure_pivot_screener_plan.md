## 1. 背景と目的

チャート表示用に実装済みの LL-HL 構造ピボットを、**スクリーナー／バックテストからも
使えるようにする**。目的は「採用する」ことではなく、**実エンジン（型1＋型3）で
採否を判定できる状態にする**こと。

### なぜ今やるか（実測の要約）

2026-08-22〜25 に本番 Parquet（個別・active 2,882銘柄 / 2021-03〜2026-03 /
流動性床 $2M）で読み取り専用の実測を重ねた。判断が2回反転しているので経緯を残す。

| 段階 | 測ったもの | 結論 |
| :--- | :--- | :--- |
| ① 単独評価 | 構造の状態・ピボット上抜け | ヌルを下回る。**採用しない** |
| ② 改良版(Advanced)の単独評価 | fib 0.618 / 本ピボット上抜け | 16通りすべて ±0.25pp 以内。**採用しない** |
| ③ **組み合わせ評価** | ADV特徴量8種 × 既存指標12種 = 4,063通り | **群として検証期に耐える。方針を反転** |

③ の要点（`tmp/probe_adv_combo.py` / `tmp/probe_adv_finalists.py`。学習 2021-03〜2024-03 で
選抜 → 検証 2024-03〜2026-03 で答え合わせ、**各期間のヌルからの超過**で比較）:

| 群 | 学習上位50 の超過 | → 検証 | 検証で正 |
| :--- | ---: | ---: | ---: |
| ADV を含む群（4,063通り） | +0.89pp | **+0.86pp** | 78% |
| 対照群（ADV なし・660通り） | +0.37pp | +0.49pp | 84% |

素の Structure Pivot は同じ手順で +1.27pp → +0.44pp（正56%）と崩れた。今回は劣化していない。
**探索の自由度が6倍ある側が劣化しないのは、当てはめではなく情報がある兆候。**

効いている項は勝率ではなく **`ピボットまでの距離 <= 2%`**（ブレイク直前）だった。
ADV 項を抜いたアブレーション:

| | 学習 | 検証 |
| :--- | :--- | :--- |
| `ピボットまで<=2% × 52週高値10% × VCR収縮 × 買い集め` | 0.57件/日 **+1.11pp**±0.84 勝率62.2% | 0.71件/日 **+2.07pp**±0.90 勝率64.1% |
| （ADV 項を抜く） | 2.81件/日 **-0.38pp**±0.32 勝率52.4% | 4.50件/日 +1.57pp±0.34 勝率64.5% |
| （近接を既存列 `63日高値4%` で代用） | 2.01件/日 -0.50pp±0.36 勝率52.7% | 3.29件/日 +1.60pp±0.38 勝率66.9% |

**学習期に土台がヌルを有意に下回る(-0.38±0.32)ところを、構造ピボット近接が有意に上へ
引き上げる(+1.11±0.84)。既存列による近接では再現しない。** 長さ帯 2-5 / 2-10 の両方で再現。
検証期は両者とも正で差は CI 内であり、**20営業日の代理指標ではここが限界**。

### 2.2 変更しないこと（確定した設計判断）

| 論点 | 判断 | 理由 |
| :--- | :--- | :--- |
| Advanced 版の出口管理（3段階ストップ・fib TP） | **入れない** | 出口は `[exit_rules]` で全戦略共通に固定されている（§6.4）。ここを触ると既存戦略との比較が全部やり直しになる。実測でも `rt_2nd_break` は平均勝ち +5.79% / 平均負け -9.91% ＝ ヌルに並ぶだけで勝率 68.6% が必要（実績64.4%）で、単体では成立していない |
| `rt_1st_break` / `rt_2nd_break` をイベントフィルタとして追加 | **入れない** | ①②の実測でヌルを上回らなかった。効いたのは「ブレイク直前」という**状態**であって上抜けイベントではない |
| ショート側（HH-LH） | **やらない** | 買い候補探しが目的（2026-08-22 ユーザー判断） |
| 長さ帯 | **2-5 に固定。チャート表示も 2-5 へ揃える**（ユーザー判断 2026-08-26） | 実測ではどちらの帯でも効果が再現し統計的な差は無い（2-5: 学習+1.11/検証+2.07、2-10: 学習+1.18/検証+2.37）。**「画面で見えている水準」と「スクリーニングされる水準」を一致させる**ことを優先し、改良版 Advanced Structure Pivot の既定（2-5）に合わせる。出荷済みチャートの既定（2-10）を変更する |
| `sp_len`（勝者の長さ）をカラム化 | **しない** | 保存した勝者に対する事後フィルタは「その帯で探索し直す」のと等価にならず（別の長さで成立していた構造を取りこぼす）、最適化軸として機能しない。帯は固定する |
| `sp_tp1_pct` を仮想カラム化 | **しない** | `tp1 - close = -risk + 1.764×range` で `sp_range_pct` と `sp_risk_pct` の線形結合。冗長 |
| `is_sp_setup` の bool カラム | **作らない** | `min_/max_sp_*` フィルタは NULL 行を自然に落とすため不要 |
| T4（相対ランク）への追加 | **しない** | 構造ピボットは銘柄内の絶対水準であり、横断パーセンタイルに意味が無い |

## 3. 変更内容

### 3.1 `indicators/structure_pivot.py` — 時系列 API の追加

描画用の `find_structures()`（構造のリストを返す）とは別に、**T3 用に1本ずつの配列**を返す
関数を足す。内部の `_scan_for_length()` を共用するので検出ロジックは1つのまま。

```python
def structure_pivot_series(high, low, close, min_len=2, max_len=5)
    -> tuple[np.ndarray, np.ndarray]:
    """各バーの (sp_pivot, sp_hl) を返す。構造が生きていないバーは NaN。"""
```

各バーで Tightest（ピボット価格が最小）の勝者を選ぶのは描画と同一。

**あわせて `DEFAULT_MAX_LEN` を 10 → 5 に変更する**（§2.2）。チャート API の既定も
2-5 になるため、`doc/frontend_specification.md` §3.3 と
`doc/completed/structure_pivot_chart_plan.md` の記述も更新する。
既存テスト（`test_structure_pivot.py` / `test_chart_api.py`）は既定値に依存する
アサーションがあるため追随させる。

### 3.2 T3 カラム

| カラム | 型 | 内容 |
| :--- | :--- | :--- |
| `sp_pivot` | FLOAT | ブレイクアウト水準（LL と HL の間の最高値）。構造が無いバーは NULL |
| `sp_hl` | FLOAT | HL の価格。**そのまま損切り候補**。同上 |

`indicators/calculate.py::calculate_indicators()` に算出ステップを追加する。

> [!IMPORTANT]
> **確定遅延を崩さないこと。** ピボットは `L` 本先まで確定しないため、実装は
> `confirmed_index = hl_index + length` 以降にしか値を入れない。ここを崩すと
> **型1バックテストは検出数と質を最適化するので、先読みが入っても成績が良くなるだけで
> 気付けない**。回帰テストは `test_structure_pivot.py` に既にある
> （`test_structure_is_not_visible_before_confirmation`）ので、T3 経路にも同種のテストを置く。

### 3.3 仮想カラム（`close` から導出。T3 カラムは増やさない）

| 名前 | 式 | 用途 |
| :--- | :--- | :--- |
| `sp_dist_pivot_pct` | `(sp_pivot - close) / close * 100` | **実測で効いた項。** 「ブレイクまであと何%」 |
| `sp_range_pct` | `(sp_pivot - sp_hl) / close * 100` | 構造の高さ。小さい＝タイトな保ち合い |
| `sp_risk_pct` | `(close - sp_hl) / close * 100` | 損切り候補までの距離。**固定 -8% ストップとの整合を見る**（実測では -8% より深い候補が 24〜41% ある） |

「ブレイク直前」は `min_sp_dist_pivot_pct = 0.0` ＋ `max_sp_dist_pivot_pct = 2.0` の
2キーで表現する（上抜け済みは負値になるので下限で除外）。**特殊フィルタは不要**で、
レジストリの汎用 `min_`/`max_` 機構に載る。

登録先は**3箇所すべて**（§7.2 の必須手順）:

| 場所 | 内容 |
| :--- | :--- |
| `indicators/screener_registry.py::VIRTUAL_COLUMNS` | 名前だけ |
| `api/screener_router.py::_VIRTUAL_COLUMNS` | SQLAlchemy 式（断面取得用） |
| `backtest/backtest_screener.py::apply_filters_to_df` | pandas 導出（**唯一の評価エンジン**） |

### 3.5 Parquet 全期間のバックフィル（**ここが本タスクの山**）

> [!WARNING]
> **`tools/deploy_after_merge.ps1 -RebuildFrom T3` だけでは不足する。**
> 同スクリプトが呼ぶ `backend/scripts/deploy_after_merge.py` は
> **ホット期間730日のみの再計算**で、それ以前の Parquet 履歴は旧値のまま残る
> （同ファイル L113 のコメントに明記）。既存カラムの値を直すだけなら問題ないが、
> **新規カラムでは残り5年分が NULL になる**。バックテスト期間は 2021-03〜2026-03 の
> 5年なので、そのままでは大半が欠損する。

`backend/pipeline/parquet_recompute.py::recompute_indicators()` が
「全銘柄・全期間の T3 を作り直す」primitive として既にある（`restore_truncated_symbol_history.py`
等が利用）。これを全銘柄に対して回すバックフィルスクリプトを新設する。

**安全弁**: 再計算は全 63 列を作り直すため、**既存カラムの値が変わっていないことを検査する**。

- 再計算結果と現行 Parquet を `(symbol_id, date)` で突合
- **既存カラムがすべて一致（float は相対誤差 1e-9）することを必須条件**にする
- 差分が出たら**昇格せず停止**して原因を報告する（指標ロジックが過去に変わっていた場合の検出）

### Parquet の作り直しについて（2026-08-26 の追加指示への回答）

> 「必要ならバックアップを取って Parquet も1から作成し直してよい」

**その許可は受け取ったうえで、原則は使わない方針とする。** 理由は上流の限界:

- 全期間再構築は yfinance から取り直す操作であり、**上流が返さなくなった銘柄の履歴を失う**。
  実績として 2026-08-02 に 17銘柄・8年分を喪失している
  （`.claude/skills/parquet-data-quality/SKILL.md` §6・§9、`backend/scripts/archive_parquet_master.py`）
- 退役・改称済みの旧ティッカーは `symbols` ごと消える（2026-08-06 に18件）
- `symbols.id` が再採番され、`user_data.db` の付け替えが必要になる（2026-08-06 に 2,378件変化）

**§3.5 の「既存の Parquet を読んで T3 だけ作り直すバックフィル」なら、上流に一切触らず
価格履歴を失わない。** こちらを本線とする。バックフィルが技術的に破綻した場合に限り、
`archive_parquet_master.py` で退避したうえで再構築へフォールバックし、
**その判断は実行前にユーザーへ報告する**。

### 5.6 Trend Line Break の移植（2026-08-29）

作者の `rt_cnt_break` を移植した。**要約から実装して2箇所を取り違え、
本番に間違った値を入れてから気付いた**ので、経緯を残す。

#### 何が起きたか

| 段階 | やったこと | 結果 |
| :--- | :--- | :--- |
| 1 | 解説記事の**要約**を読んで実装。1年ぶんの価格で検証 | 43件・作者2件 **2/2**。「一致した」と報告した |
| 2 | T3 に載せて本番昇格 | スクリーナー経路で **1/2**。BHVN が落ちた |
| 3 | 原因調査 | アンカー1 の探索窓が青天井で、**履歴の長さで値が変わる**と判明 |
| 4 | 窓（250〜1000本）を入れて経路一致を確保 | 経路一致 100%。ただし作者との一致は **0/2** に |
| 5 | ユーザーの指摘で**記事から Pine 原文を取得** | 2箇所の取り違えが判明（下記） |
| 6 | 原文どおりに実装し直して再昇格 | **31件・2/2 かつ 経路一致 100%** |

#### 取り違えていた2箇所

**(1) 傾きは最大化。最小化ではない。**

```pine
if find_highs
    if m > best_slope
        update_best := true
```

要約の「最も急な下向き傾き」をそのまま最小化で実装していた。
アンカー1 が最高値なので後続は必ず下向きになり、**最大化＝最も浅い下り
＝後続の高値を上から包む線**になる。ここを逆にすると別物の線が出る。

**(2) 候補点は「窓の中の全ピボット」ではない。**

原文の `arr` は**長さごとの状態機械が持つ prev / curr の2点だけ**
（帯 2-5 なので最大8点）。全ピボットから探していたため、履歴が長いほど
古くて高い点が選ばれ、値が履歴の長さに依存していた。

あわせて `slope < 0` の判定も外した（原文に無い）。無くても成り立つのは、
アンカー1 が `idx <= limit_idx` の最大値で、アンカー2 の候補が
`a1 < idx < limit_idx` に限られるため。傾きは構造上つねに 0 以下。

なお `rt_cnt_break` は原文でも **当日のライン値で前日終値を判定**している
（`close[1] <= cnt_val_long and close > cnt_val_long`）。
スクリーナー実装の「前日のライン値を当日の値で代用」は近似ではなく原文どおり。

#### なぜ (2) が実害だったか

`t3_indicators.py` L22 は **SQLite の daily_prices ＝ 直近730日（約500本）**しか
読まない。一方 Parquet のバックフィルは**全期間（平均約1,880本）**を読む。
値が履歴長に依存すると、**バックテスト（Parquet を直読み）と
スクリーナー（日次更新が書いた値）が別条件を評価する**。

実測: 最終バーの **12%**、直近60本の **44%** が食い違っていた。
原文どおりなら候補が直近の数ピボットに限られるので、この問題は構造的に起きない。

#### 検証（本番 Parquet 全期間・個別 active 2,872銘柄）

| 版 | 検出 | 作者2件 | 経路一致 |
| :--- | ---: | :--- | :--- |

### 失敗の所在（2026-08-26 の追加診断）

「勝率が高いのに成績に繋がらないのは E と同じ問題では。エントリータイミングの
傾向はあるか」という問いに対して、トレードログを本番データと突き合わせた。

#### エントリータイミングは問題ではない

| | H1（ブレイク前に買う） | E1（比較） |
| :--- | ---: | ---: |
| エントリー後にピボットを上抜けた | **80.6%** | 86.8% |
| 抜けるまでの日数（中央値） | **0日** | 0日 |
| 最大含み益 MFE（中央値） | **+2.88%** | +2.74% |
| 最大含み損 MAE（中央値） | -1.53% | -1.32% |
| EMA21 で決済 | 90% | 83% |
| -8%ストップに刺さる | 3% | 0.4% |

**8割が当日にブレイクしている。** 「早すぎて抜けなかった」のではなく、
**抜けた後に伸びない**（MFE 中央値 +2.88%）。B5 は 56% が -8%ストップに刺さる代わりに
勝ちが +35.1% 伸びる。これは**タイミングではなく銘柄選定の差**。

#### アブレーション（診断用の一時戦略。実施後に config から除去済み）

| 戦略 | Trades | AvgWin | AvgLoss | AvgGain | **Alpha** |
| :--- | ---: | ---: | ---: | ---: | ---: |
| **H1**（構造ピボット × VCR収縮 × 高値近接 × 買い集め） | 360 | +7.4% | -3.0% | +0.98% | **+0.02%** |
| H1x_vcr_only（**構造ピボットを外す**） | 993 | +7.1% | -3.2% | +0.33% | **-0.33%** |
| H1x_no_vcr（**VCR を外す**） | 4,805 | +9.2% | -4.4% | -0.01% | **-0.30%** |
| H1x_momentum（構造ピボット × RSランク上位20% × TT） | 5,594 | +10.2% | -4.6% | +0.22% | **-0.24%** |

**当初の仮説「VCR（静かな銘柄）が profile を悪くしている」は外れ。**
VCR を外すと Alpha は +0.02% → **-0.30%** に悪化する。VCR は助けていた。

読み取れること:

1. **構造ピボットも VCR も、それぞれ +0.3pp 程度のアルファ寄与はある**
   （外すとそれぞれ -0.33% / -0.30% へ落ちる）。実測で見えた効果は本物だが**小さい**
2. **両方足してようやくゼロ**。どちらか一方では確実にマイナス
3. **緩めると検出数が10倍以上に増え、質が崩壊する**（360 → 4,805 / 5,594 件）。
   「量は質の代理変数として負に働く」という既知のパターンがここでも出た
4. **モメンタム条件と組んでも伸びない**（H1x_momentum: AvgWin +10.2% と、
   B5 の +35.1% には遠く及ばない）。**構造ピボットが選ぶ銘柄は走らない**

「ピボットの 2% 下」という状態は、保ち合い・平均回帰寄りの局面を指しており、
B 系が捉えているもの（テーマ主導＋RSモメンタム）とは**構造的に別種の銘柄**を選んでいる。
これが「勝率は高いが伸びない」の正体であり、E 系と同根。

### 最適化後の比較（2026-08-26。これが最終判定）

素のアブレーションは**検出件数が 360 vs 4,805 と桁違いになり比較として成立していなかった**
（フィルタを外すと「項の有無」と「件数」が同時に動く。件数と質は負相関）。
ユーザー指摘を受け、**両者を同条件で最適化してからベスト同士を比べ直した**。

対照群 `H1c_no_pivot_control` は H1 から**構造ピボットの2キーだけ**を抜き、
他の条件・探索レンジ・検出件数ゲートは完全に同一。各100 trials。

| | in-sample スコア | パラメータ |
| :--- | ---: | :--- |
| **H1（構造ピボットあり）** | **-0.397** | `max_sp_dist_pivot_pct=2.0` / `min_dist_52w_high_pct=-12.5` / `max_vcr=0.7` / `min_up_down_vol_ratio_50=1.25` |
| **H1c（構造ピボットなし）** | **+0.205** | `min_dist_52w_high_pct=-10.0` / `max_vcr=0.65` / `min_up_down_vol_ratio_50=1.25` |

**構造ピボットを外した方が良い。** 素のアブレーションでは「構造ピボットが +0.35pp 寄与」と
読めたが、あれは緩い側が件数で不利を被っていただけで、**符号が逆だった**。

H1c のベスト実測: Port CAGR 5.18% / 最大DD -32.4% / Expectancy 0.470% /
**Expectancy LCB -0.810%**（＝統計的にはゼロと区別できない）/ AvgGain 0.470%。

H1 のホールドアウト（`[[optimization_validation.sets]]`）:

| セット | trades | 勝率 | expectancy | LCB | DD |
| :--- | ---: | ---: | ---: | ---: | ---: |
| stress_bear（2018Q4+COVID） | 45 | 66.7% | +3.94% | +0.35% | -29.5% |
| calm_recent（2023+2026H1） | 185 | 43.2% | +0.75% | **-0.27%** | -39.7% |

**最終判定: スクリーン条件として不採用。**
構造ピボットは足す価値が無いどころか、同じ枠を使うなら**外した方が良い**。
対照群自身も LCB が負でゼロと区別できず、H 系はどの形でも採用水準に届かない。

### T3 カラム自体は残す価値がある

スクリーン条件としては不採用だが、`sp_pivot` / `sp_hl` は
**チャート画面の DATA VIEW 表示（ユーザー要望）とチャート描画**で使う。
手動でエントリー価格と損切りラインを決める用途では、現行の近似（N日ローリング最大高値）より
正確な水準を出せる。本番昇格は DATA VIEW を動かすために必要。
