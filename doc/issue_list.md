    ```python

    ...

  **限界1: Yahoo が分割記録を持っていない銘柄がある**
  `auto_adjust=True`（yfinance 1.3.0 の既定）は Yahoo 自身の分割・配当記録に依存する。記録が欠けている銘柄では調整が行われず、生の価格ジャンプがそのまま残る。**何度取り直しても直らない。**

  UAVS 2024-09-27 → 09-30   自社   13.50 → 4.50  ／ Yahoo   13.50 → 4.50   （完全一致）
  ```
  2026-07-30 に Parquet を全消去して全期間を取り直した後も 299 件が残ったことで確認済み。

  **限界2: 調整は「現在のティッカー」にしか反映されない（遡及的）**
  分割調整は過去の全価格を遡って書き換えるが、その修正が載るのは**現行ティッカーの系列だけ**。改称・廃止された旧ティッカーの系列は、死んだ時点の未調整の姿で凍結される。
  ```
  EDOC（旧）  2020-07-30 〜 2025-09-01 は HEAL の 1/3 の水準（1:3 併合が未調整）
  HEAL（新）  全期間が調整済みの連続系列
  → 旧ティッカーで取り直す限り壊れたデータしか得られない。改称してはじめて直る。
  ```
  こちらは**改称を universe.db に反映すれば解消する**（`backend/scripts/rename_symbol.py`）。実際 `EDOC` → `HEAL` でアノマリー一覧から消えた。

  **限界3: 日次の差分取得では過去の調整が反映されない**
  T2 は `current_max + 1日` からの差分取得なので、分割が起きても既存の行は書き換わらない。調整済みの新しい行が未調整の古い行に継ぎ足され、分割日に段差が残る。**これは限界1・2と違い、全期間の取り直し（`run/tool/refresh_All.bat`、Parquet クリーン `y`）で解消する。**

  **対応の方向性**
  | 限界 | 解消手段 |
  | :--- | :--- |
  | 1（ソースに記録が無い） | 再取得では不可。補正テーブルを自前で持つ / 別ソースを併用 / 該当銘柄を母集団から除外 |
  | 2（改称ティッカー） | `rename_symbol.py` で universe.db に改称を反映 |
  | 3（差分取得の継ぎ接ぎ） | 定期的な全期間再構築 |

  検出は `weekly_maintenance.py` のアノマリー監査が担うが、**価格比だけでは「未調整の分割」と「実際の急騰」を判別できない**（売買代金の連続性を併用する。下記エントリ参照）。

  ### yfinance / Yahoo Finance のその他の既知の限界（すべて 2026-07-28〜31 に実測で確認）

  **A. HTTP 404 と 429 を同じメッセージに畳む — 最も危険**
  `yf.download` はどちらも `possibly delisted; no price data found` を返す。**「ティッカーが存在しない」と「レート制限で弾かれた」が区別できない。**
  実際この誤読で「45銘柄は T2 の差分取得ロジックの穴が原因」と誤診断し、本番の55行を不要に削除した（2026-07-29）。
  **切り分け方**: Yahoo chart API（`query1.finance.yahoo.com/v8/finance/chart/{ticker}`）を直接叩き HTTP ステータスを見る。429 なら SPY 等の正常銘柄も同時に失敗する。個別銘柄だけ 404 なら供給側の問題。

  **B. レート制限（429）を踏みやすい**
  数十リクエストの連続で 429 になる。3,000銘柄規模の一括取得では部分失敗が起きうる。
  **特に危険なのは、部分的に成功したとき**: T2 は `current_max + 1日` からの差分取得に切り替わるため、1行でも入ると過去を二度と取りに行かない（自己修復しない）。
  → 大規模再取得の後は必ず鮮度監査を行い、`no_history` に落ちた銘柄を個別に取り直すこと。

  **C. タイムスタンプ行はあるのに OHLCV がすべて null になる（部分的な供給停止）**
  `^VIX3M` が 2026-07-20〜07-29 の8営業日、`AVNS` `KORE` `TMHC` が 07-20〜07-30 で発生。`^VIX` `SPY` `AAPL` `ALNY` は正常だったため、**一部銘柄だけの系統的な障害**。再構築でも直らない。
  行数が十分にあるため「履歴なし」判定に引っかからず、**上場廃止候補に紛れて埋もれる**（`^VIX3M` で実際に発生）。

  **D. 死んだティッカーが「残骸1行」を返す**
  改称後の `FDP` `IAC` `VSCO` はいずれも `2026-07-17` の1行だけを返した。完全な 404 ではないため、
  **「まだ生きている」と誤判定させる**。`retire_stale_symbols.py` の供給側検証はこれを `alive` と見て
  スキップする（保守的なので実害は無いが、改称の検出が自動化できない理由になっている）。

  **E. `range=max` は `interval=1d` を指定しても日足を返さない**
  `JPY=X` で `range=max` は 358行（月足）を返した。日足が必要なら `period1` / `period2` を明示すること。
  ```
  range=max        358行（12行/年 = 月足）1996-11-01 〜
  period1=0 明示  7,759行（日足）        1996-10-30 〜
  ```

  **F. 日付のタイムゾーン変換を誤ると存在しない土日行が生成される**
  chart API のタイムスタンプを UTC で変換すると、為替（`JPY=X`）で金曜バーが土日にずれ込んだ。
  `meta.exchangeTimezoneName`（`JPY=X` なら `Europe/London`）で変換すれば月〜金のみになる。
  ```
  UTC 変換            Mon1552 Tue1551 Wed1552 Thu1552 Fri649 Sun903  ← 土日が発生
  Europe/London 変換  Mon1552 Tue1551 Wed1552 Thu1552 Fri1552       ← 正常
  ```

  **G. 同じ問い合わせでも結果が揺れる**
  `^VIX3M` を `range=1mo` で照会した際、ある時点では「07-29 に有効値あり」と返り、後の照会では
  「07-29 は null / 07-30 に値あり」になった。**1回の照会結果を根拠に恒久的な判断（退役等）をしないこと。**

  **H. `auto_adjust` の既定値に依存している（潜在リスク）**
  `data_collection/fetcher.py` の `yf.download()` は `auto_adjust` を明示していない。
  現在の yfinance 1.3.0 では既定 `True`（＝分割・配当調整済み）だが、**この既定値はバージョンによって変わりうる**。
  変わると DB 全体の価格基準が黙って切り替わる。**明示指定すべき。**

  **I. `fetch_daily_data` の `df.ffill()` が欠損を埋めてしまう（潜在リスク）**
  `data_collection/fetcher.py:55` は取得直後に無条件で `df.ffill()` を実行する。実測：
  ```
  ffill 前   Open=NaN  High=NaN  Low=NaN  Close=NaN  Volume=NaN
  ffill 後   Open=100  High=101  Low=99   Close=100.5  Volume=1000   ← 前日値で完全に埋まる
  ```
  **出来高まで前日値で埋まる**ため、存在しない取引日を捏造して DB に格納しうる。
  上記 C（部分的な供給停止）と組み合わさると危険。
  現状 `^VIX3M` の欠損日が DB に入っていないのは **yfinance 側が全 NaN 行を落としているため**であって、
  こちらの防御が効いているわけではない。**一部の列だけ NaN で返った場合は捏造される。**
  コメントは「weekends/holidays that somehow ended up as NaNs」とあるが、
  yfinance は営業日以外の行をそもそも返さないため、この ffill が救う想定ケースは実在しない可能性が高い。

- [x] **`stocktool.db` の肥大化と WAL チェックポイントの恒常的な失敗（2026-07-28 発見 / 2026-08-07 真因特定・修正）**

  ### 真因（当初の診断は誤りだった）

  当初は「読み取り接続に阻まれている」と診断していたが、**それは主因ではなかった**。
  2026-08-07 に同じ処理を2経路で実行して切り分けた。

  | 経路 | 結果 |
  | :--- | :--- |
  | A. 現行実装（write セッションで `PRAGMA`） | **失敗** `database table is locked` |
  | B. 独立した生コネクションで `PRAGMA` | **成功** `(0,0,0)` / WAL 11.6MB → 0 |

  `write_engine` は `begin` イベントで **`BEGIN IMMEDIATE`** を張るため、
  `db.execute(text("PRAGMA wal_checkpoint(TRUNCATE)"))` は暗黙のトランザクションに入り、
  SQLite がトランザクション内のチェックポイントを拒否していた。
  **他に誰も居なくても必ず失敗する** — つまり**このフェーズのチェックポイントは
  一度も成功していなかった**。「恒常的に失敗」の説明がこれでつく。

  ### 併せて実測した「読み取りに阻まれた場合」

  読み取りトランザクションが開いていると、**どのモードでも1フレームも回収できない**。

  ```
  PASSIVE   busy=0 log=506  checkpointed=0   ← 成功に見えるが回収ゼロ
  FULL      busy=1 log=1012 checkpointed=0
  TRUNCATE  busy=1 log=1518 checkpointed=0
  ```

  **`PASSIVE` への変更は解決にならない**どころか、`busy=0` を返すので問題が見えなくなる。
  TRUNCATE のまま**結果を数値で報告する**方針を採った。

  ### 修正内容

  - `orchestrator.safe_wal_checkpoint`: commit 後に**独立した生コネクション**で実行。
  - **`CHECKPOINT_BUSY_TIMEOUT_MS = 3000`**: `write_engine` は `timeout=3600` なので、
    その接続を使うと阻まれたとき**最大1時間パイプラインが止まる**（テストで実際にハングして発覚）。
    回収は best-effort なので待たずに諦める。
  - `describe_checkpoint_result`: `busy=0` でも回収ゼロなら成功扱いしない。
    SQLite が返す `-1`（チェックポイントを開始すらできなかった）も区別する。
  - 週次メンテ: VACUUM の前に WAL を回収（`checkpoint_wal`）、
    `classify_wal_size()` が 100MB 超を警告、レポートに「8. Physical size」節を追加。
    **ログの WARNING は流れて消えるため、レポートに数値で残すことが検知の要。**
  - テスト14件（`backend/tests/pipeline/test_wal_checkpoint.py`）。
    本丸は「呼んだら WAL が実際に回収されること」— これが無かったため
    「呼んでいるのに一度も効いていない」に誰も気づけなかった。

  ### 本番での実証（2026-08-07 の日次パイプライン）

  ```
  07:43:53 [WARNING] WAL checkpoint を開始できませんでした（busy=1）   ← 別作業と衝突
  07:51:37 [INFO]    WAL checkpoint: 回収済み（WAL は空）              ← 2,442MB を回収
  07:53:23 [INFO]    WAL checkpoint: 回収済み（WAL は空）
  08:00:46 [INFO]    WAL checkpoint: 回収済み（WAL は空）
  ```

  ### 週次メンテの終了時にも回収する（2026-08-07 追加）

  物理メンテ（checkpoint → REINDEX → VACUUM）は**監査より前**に走るため、
  その後の監査・SEC 同期の書き込みが WAL に積まれたまま終わっていた。実測:

  ```
  08:18:57  VACUUM 完了   DB 6,086MB → 1,575MB（74.1% 回収）
  08:19:11  監査完了後 …  -wal 1,584 MB が残存 → レポートが <<< CHECK を出した
  ```

  **新設した監視が初回で実問題を検知した。** 監査後にも `checkpoint_wal()` を実行するようにした。

  ### 現況（2026-08-07）

  ```
  DB    6,085.95 MB → 1,574.70 MB   （74.1% 回収 / VACUUM 70秒・REINDEX 79秒）
  -wal  1,583.9 MB  → 0.0 MB
  ```

  `architecture.md` §11.1 の想定 1.7GB 前後に収まった。

  ### 残る運用上の注意

  **重い読み取り（シナリオテスト・最適化）を走らせたまま日次パイプラインを回すと、
  その瞬間のチェックポイントは依然として回収できない。** ただし失敗しても次のフェーズで
  回収されるようになったため、以前のように WAL が積み上がり続けることはない。
  週次レポートの「8. Physical size」で `-wal` が 100MB を超えていないか確認すること。

  従来は削除に**1回失敗しただけで即座に `DROP ALL TABLES`** へ落ちていた。
  2026-08-06 の実測では、掴んでいたのは uvicorn で、そのまま DROP ALL に進んだ結果
  **読み取りロックに阻まれて5分以上ハング**し（CPU 8秒）、プロセスを落として

  - `delete_with_retry()`: 2秒間隔で5回まで粘る（終了直前のリクエスト程度の一過性は吸収）
  - `describe_lock_holders()`: **同じプロジェクトを触っている Python プロセスを名指し**する
  - 既定では**中断**し、逃げ道として `--force` で従来のフォールバックを残した

  > [!WARNING]
  > **`psutil.Process.open_files()` は使えない。** Windows で `access violation` を起こし
  > **インタプリタごと落ちる**（`except` で捕捉不能。2026-08-09 にテスト実行時に実測）。
  > そのため「そのファイルを開いているプロセス」の厳密な特定は諦め、
  > プロジェクトルートを含む cmdline の Python プロセスを候補として挙げている。

  ### 実証

  ```
  週次メンテ相当がロックを保持中 → run_production_restore は PipelineLockBusy で中断 (exit=1)
  uvicorn 稼働中に復元を実行     → 5回リトライ後、uvicorn を名指しして中断（DROP ALL に進まない）
  ```
